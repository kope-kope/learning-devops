# DevOps Learning Log — 05-28-2026

## Q1: What is `netstat -antp` for Mac?

**Short answer:** On Mac, the closest equivalent is `netstat -an -p tcp` or, better yet, `lsof -i -n -P`.

**Why it's different:** `netstat -antp` is a Linux command. The flags mean:
- `-a` — show all connections (listening + established)
- `-n` — numeric addresses (don't resolve hostnames)
- `-t` — TCP only
- `-p` — show the PID/program name owning each socket

macOS uses a BSD-derived `netstat`, not the Linux (net-tools) version. BSD `netstat` doesn't support `-t` or `-p` the same way.

**Mac equivalents:**

```bash
# Option 1: BSD netstat (no PID info)
netstat -an -p tcp

# Option 2: lsof (recommended — includes PID + process name)
sudo lsof -i -n -P

# Option 3: filter to listening TCP sockets with process info
sudo lsof -iTCP -sTCP:LISTEN -n -P
```

**Why `lsof` is better on Mac:**
`lsof -i` gives you everything `netstat -antp` gives on Linux — open sockets, protocol, local/remote address, state, AND the process name + PID. BSD `netstat` can't show you which process owns a socket, which is usually the whole reason you're running the command.

**Key flags for `lsof -i`:**
- `-i` — list network connections
- `-n` — don't resolve hostnames
- `-P` — don't resolve port names (show numbers)
- `-iTCP` / `-iUDP` — filter by protocol
- `-sTCP:LISTEN` — filter to listening sockets only

## Q2: What is `ifconfig` and why doesn't it work?

**What it does:** `ifconfig` (interface configuration) shows you your network interfaces and their IP addresses, MAC addresses, subnet masks, and status (up/down). It's how you answer "what's my IP address?" from the command line.

**Why it doesn't work:** It depends on your OS:
- **Linux:** `ifconfig` is part of the legacy `net-tools` package. Modern distros don't install it by default anymore. It's been replaced by `ip`.
- **Mac:** `ifconfig` *should* work out of the box — it's built in. If it's not found, your `$PATH` might be broken. Try the full path: `/sbin/ifconfig`.

**The modern replacement on Linux is `ip`:**

```bash
# Old way (ifconfig)
ifconfig

# New way (ip) — preferred on Linux
ip addr show        # show all interfaces and IPs
ip a                # shorthand for the above
ip link show        # show interface status (up/down)
ip route show       # show routing table (replaces `route`)
```

**On Mac, `ifconfig` still works fine:**

```bash
ifconfig                    # all interfaces
ifconfig en0                # just Wi-Fi (typically)
ipconfig getifaddr en0      # quick way to get just your IP
```

**Why Linux moved away from `ifconfig`:**
The `ip` command (from `iproute2`) handles modern networking features that `ifconfig` can't — multiple IPs per interface, network namespaces, policy routing, etc. `ifconfig` was designed for simpler times. If you're doing DevOps on Linux, get comfortable with `ip` — you'll see it everywhere in containers and cloud VMs.

## Q3: Reading `ip addr show` output — three interfaces, three networks?

**Not exactly three networks. Two real networks + one virtual loopback.**

### Interface breakdown:

**1. `lo` (loopback) — not a real network**
- IP: `127.0.0.1/8`
- This is your machine talking to itself. Every Linux box has this. When you hit `localhost` or `127.0.0.1`, traffic never leaves the machine — it loops back. Not a network connection.

**2. `eth0` — first real network (NAT/internet-facing)**
- IP: `172.16.184.147/24`
- `dynamic` keyword = this IP was assigned by DHCP (a router/server gave it to you)
- `valid_lft 1395sec` = the DHCP lease expires in ~23 minutes, then it renews
- `172.16.x.x` is a private IP range — this is likely a NAT adapter giving your VM internet access through the host machine

**3. `eth1` — second real network (host-only)**
- IP: `192.168.56.11/24`
- `valid_lft forever` = static, no lease expiration — this was configured manually or by the hypervisor
- `192.168.56.x` is the classic VirtualBox/VMware host-only network range — this lets your host machine and VM talk to each other directly, with no internet access

### So the real answer:
You're on a VM (VMware or VirtualBox) with a **dual-NIC setup** — one adapter for internet access (eth0, NAT) and one for direct host-to-VM communication (eth1, host-only). This is a very common lab/DevOps setup. The loopback doesn't count as a network connection.

### Key details to notice in this output:
- `/24` after the IP = subnet mask of 255.255.255.0 (254 usable hosts on that subnet)
- `brd` = broadcast address for the subnet
- `link/ether` = the MAC address of that interface
- `state UP` = interface is active
- `scope global` = routable on the network; `scope host` (on lo) = only reachable from this machine
- `scope link` (on the inet6 lines) = only reachable on the local network segment

## Q4: How many networks can a machine connect to?

**There's no hard limit from the OS.** Linux can handle hundreds of network interfaces. The real constraints are:

**Physical NICs:** A typical server has 2-4 physical ethernet ports. High-end servers might have 8+. Each one is a connection to a different physical network.

**Virtual NICs:** This is where it gets interesting for DevOps. A VM or container can have as many virtual NICs as the hypervisor allows. VirtualBox caps at 8 per VM. VMware allows up to 10. But on bare metal Linux, you can create hundreds of virtual interfaces.

**Examples of virtual interfaces you'll encounter in DevOps:**
- `veth` pairs — how Docker containers connect to the host
- `br0`, `docker0` — bridge interfaces (virtual switches)
- `tun0`, `wg0` — VPN tunnels (WireGuard, OpenVPN)
- `bond0` — bonded interfaces (multiple physical NICs acting as one)
- `vlan100` — VLAN-tagged sub-interfaces

A single Docker host might easily have 50+ `veth` interfaces — one per running container. A Kubernetes node can have hundreds.

**So the practical answer:**
- Laptop/desktop: 1-3 (Wi-Fi, ethernet, maybe a VPN)
- VM in a lab: 2-4 (what you have now)
- Production server: 2-8 physical + dozens of virtual
- Docker/K8s node: hundreds of virtual interfaces

## Q5: What is the `tracert` equivalent for Mac?

**`traceroute`** — it's already installed on Mac and Linux.

`tracert` is the Windows name. Mac/Linux use `traceroute`. They do the same thing: show every router (hop) your packet passes through on the way to a destination.

```bash
# Basic usage
traceroute google.com

# Limit to 15 hops (default is 30)
traceroute -m 15 google.com

# Use ICMP instead of UDP (more likely to get through firewalls)
traceroute -I google.com

# Use TCP on port 443 (most firewall-friendly)
sudo traceroute -T -p 443 google.com
```

**How it works:**
It sends packets with incrementing TTL (Time To Live) values — starting at 1. Each router along the path decrements TTL by 1. When TTL hits 0, that router sends back an error message ("time exceeded"), revealing its IP. So:
- TTL=1 → first router replies
- TTL=2 → second router replies
- TTL=3 → third router replies
- ...until you reach the destination

**Reading the output:**
Each line is a hop. You'll see 3 round-trip times (it sends 3 probes per hop). `* * *` means that router didn't respond — it's either dropping the probes or has ICMP disabled. This is common and doesn't necessarily mean a problem.

**Also useful:** `mtr` (My Traceroute) — combines `traceroute` + `ping` into a live, continuously updating view. Install via `brew install mtr` on Mac. Great for diagnosing intermittent packet loss.

## Q6: Understanding `nslookup` output

Command run: `nslookup www.tosinoladokun.com`

**Line-by-line breakdown:**

```
Server:   127.0.0.53
Address:  127.0.0.53#53
```
This is WHO answered your DNS query — not your website. `127.0.0.53` is `systemd-resolved`, a local DNS stub resolver running on your VM. It received your query, forwarded it to the real upstream DNS server (e.g., your ISP's or Google's 8.8.8.8), got the answer back, and relayed it to you. The `#53` is the port — DNS always runs on port 53.

```
Non-authoritative answer:
```
This means the answer came from a **cache**, not from the DNS server that actually owns (is "authoritative" for) `tosinoladokun.com`. Your local resolver or an upstream resolver had it cached from a previous lookup. The answer is still correct — "non-authoritative" just means it's secondhand.

An **authoritative** answer would come from whichever DNS provider hosts your domain's records (e.g., Cloudflare, Namecheap, Route53).

```
Name:    www.tosinoladokun.com
Address: 216.198.79.1
```
This is the DNS answer: `www.tosinoladokun.com` resolves to IP `216.198.79.1`.

**Does this mean 216.198.79.1 is your website's IP?**

Sort of — it's the IP that DNS points your domain to. But it's not necessarily a server dedicated to just your site. It could be:
- A shared hosting server running hundreds of sites (most likely for a personal site)
- A CDN edge node (Cloudflare, etc.) that proxies traffic to your actual server
- A load balancer sitting in front of your real server

The server at that IP uses the `Host` header in the HTTP request to figure out which website to serve. That's how one IP can host many domains — this is called **virtual hosting**.

**Follow-up: Navigating to 216.198.79.1 goes to Vercel**

This confirms the virtual hosting point above. `216.198.79.1` is a **Vercel edge server**, not a machine dedicated to `tosinoladokun.com`. Vercel hosts thousands of sites behind the same set of IPs. When you browse to `www.tosinoladokun.com`, your browser sends a `Host: www.tosinoladokun.com` header, and Vercel's server uses that to route to your specific site.

When you navigate to the raw IP `216.198.79.1` in a browser, there's no hostname — so Vercel doesn't know which site to serve. It shows its own default/landing page instead.

Note: `127.0.0.53` is your local DNS resolver (loopback address). If you typed that into a browser on the VM, you'd hit the local resolver's interface, not Vercel. It was `216.198.79.1` (your site's resolved IP) that went to Vercel.

## Q7: Which standard reserved private IP addresses, and why?

**RFC 1918** (published in 1996) is the standard that carved out private IP ranges from each class.

### The reserved ranges:

| Class | Private Range | CIDR | # of Addresses |
|-------|--------------|------|----------------|
| A | 10.0.0.0 – 10.255.255.255 | 10.0.0.0/8 | ~16.7 million |
| B | 172.16.0.0 – 172.31.255.255 | 172.16.0.0/12 | ~1 million |
| C | 192.168.0.0 – 192.168.255.255 | 192.168.0.0/16 | ~65,000 |

These IPs are **non-routable** on the public internet. Routers on the internet are configured to drop packets with these source/destination addresses.

### Why they did it: IPv4 exhaustion

IPv4 has ~4.3 billion addresses total. That sounds like a lot, but in the early 90s it became clear that the internet was growing fast enough to run out. The classful system made it worse — a single Class A allocation gave one organization 16.7 million addresses, most of which went unused.

RFC 1918 solved this by saying: **not every device needs a public IP.** Your home has one public IP from your ISP, but behind your router, your laptop, phone, TV, and smart fridge all use private `192.168.x.x` addresses. They share that single public IP through **NAT (Network Address Translation)** — the router rewrites the source IP on outgoing packets to its public IP, and maps responses back to the right internal device.

### Why this matters for DevOps:

- Your VM's `172.16.184.147` and `192.168.56.11` from Q3 — both private ranges. That's why they're not reachable from the internet.
- AWS/GCP/Azure VPCs use `10.0.0.0/8` internally. Your EC2 instance gets a `10.x.x.x` private IP plus an optional public IP via NAT.
- Docker's default bridge network uses `172.17.0.0/16` — also a private range.
- Kubernetes pod networks typically carve out of `10.x.x.x`.

Every layer of infrastructure you'll work with uses RFC 1918 ranges internally.

## Q8: What is NAT (Network Address Translation)?

**NAT is the trick that lets multiple devices share one public IP address.** A NAT device (usually a router) rewrites IP addresses in packet headers as they cross between a private network and the public internet.

### How it works — step by step:

Say your laptop (`192.168.1.5`) wants to reach `google.com` (`142.250.80.46`). Your router's public IP is `73.45.200.10`.

**Outgoing packet (your laptop → Google):**
1. Laptop sends: `src: 192.168.1.5:52340 → dst: 142.250.80.46:443`
2. Router intercepts it, rewrites the source: `src: 73.45.200.10:61234 → dst: 142.250.80.46:443`
3. Router records in its NAT table: `61234 ↔ 192.168.1.5:52340`
4. Packet goes out to the internet with the public IP

**Return packet (Google → your laptop):**
1. Google replies: `src: 142.250.80.46:443 → dst: 73.45.200.10:61234`
2. Router looks up port `61234` in its NAT table → maps to `192.168.1.5:52340`
3. Router rewrites destination: `src: 142.250.80.46:443 → dst: 192.168.1.5:52340`
4. Laptop receives the reply

Google never sees `192.168.1.5`. It only knows about `73.45.200.10`. The router handles the translation both ways using **port numbers** to track which internal device each connection belongs to. This specific form is called **PAT (Port Address Translation)** or **NAPT** — one public IP, many internal devices, distinguished by port.

### Types of NAT:

- **SNAT (Source NAT):** Rewrites the source IP. This is what your home router does — internal → external. Also what AWS does when your EC2 instance in a private subnet reaches the internet through a NAT Gateway.
- **DNAT (Destination NAT):** Rewrites the destination IP. This is **port forwarding** — traffic arrives at your public IP on port 8080, router redirects it to `192.168.1.100:80`. Also how Kubernetes `NodePort` services work.
- **1:1 NAT:** One private IP maps to one public IP. Used in AWS with Elastic IPs.

### Where you'll see NAT in DevOps:

- **Docker:** When you do `docker run -p 8080:80`, Docker sets up a DNAT rule using `iptables` — traffic hitting the host on 8080 gets rewritten to the container's private IP on port 80.
- **AWS NAT Gateway:** Lets EC2 instances in private subnets reach the internet (for updates, API calls) without having public IPs.
- **Kubernetes:** `kube-proxy` uses iptables/IPVS NAT rules to route Service traffic to the right pod IPs.
- **Your VM setup from Q3:** `eth0` (`172.16.x.x`) accesses the internet through NAT — the hypervisor's NAT adapter rewrites packets, which is exactly why that adapter type is called "NAT" in VirtualBox/VMware.

## Q9: The political story behind the OSI 7-layer model

**The OSI model was a European/institutional standards play that lost to the American/hacker-built TCP/IP — but survived as a teaching tool.**

### The two sides:

**Team OSI (ISO + European governments + telcos):**
The International Organization for Standardization (ISO) and the ITU (the UN's telecom body) wanted to design the "correct" networking architecture top-down. The OSI model was developed through formal committee processes — governments, PTTs (European state-owned telephone monopolies like France Télécom, British Telecom), and large vendors (IBM, Siemens) all had seats at the table. They wanted an officially blessed, internationally agreed-upon standard before anyone started building.

**Team TCP/IP (DARPA + US researchers + Unix hackers):**
TCP/IP was already running. DARPA funded it in the 70s, and by 1983 ARPANET had switched to TCP/IP. BSD Unix shipped with a TCP/IP stack built in. It wasn't designed by committee — researchers built it, tested it, revised it, and shipped it. The IETF's motto was "rough consensus and running code."

### What happened politically:

In the mid-1980s, governments — especially in Europe — tried to mandate OSI. The US government passed GOSIP (Government OSI Profile) in 1990, requiring federal agencies to buy OSI-compliant networking. European governments did the same. This was a deliberate political push: OSI was seen as the "proper" international standard, and TCP/IP was seen as an American military experiment that happened to work.

But TCP/IP had a massive advantage: **it already existed and was free.** BSD Unix shipped with it. When the commercial internet took off in the early 90s, everyone was already running TCP/IP. OSI protocol implementations were expensive, late, bloated, and often didn't interoperate well across vendors — the exact problem standards were supposed to solve.

By the mid-90s, the web exploded on top of TCP/IP, and OSI as a protocol suite was dead. GOSIP was quietly rescinded. Nobody was going to rip out working TCP/IP to install OSI protocols.

### Why OSI survived anyway:

The 7-layer model is a genuinely useful **conceptual framework** for thinking about networking, even though the actual OSI protocols lost. When people say "that's a Layer 7 problem" or "the issue is at Layer 3," they're using OSI vocabulary to reason about TCP/IP networks. The model outlived its own protocols.

### The lesson for DevOps:

This is a pattern that repeats in tech: designed-by-committee vs. working-code-first. You see it in SOAP vs REST, XML vs JSON, OpenStack vs AWS. The thing that ships and works tends to win over the thing that's architecturally "correct."

## Q10: OSI 7-Layer vs TCP/IP 4-Layer — differences and mapping

They're two models for the same reality, but designed with different philosophies.

### The key difference: TCP/IP is pragmatic, OSI is theoretical.

**OSI separates concerns cleanly into 7 layers.** Each layer does one thing. This is great for teaching and reasoning — you can say "that's a Layer 3 problem" and everyone knows you mean routing/IP.

**TCP/IP collapses it to 4 layers** because in practice, the boundaries between some OSI layers don't matter. Two big merges:

**Merge 1 — Top layers (L5 + L6 + L7 → Application):**
OSI separates session management, data formatting, and application logic. TCP/IP says: "the application handles all of that." When you write an HTTP server, you don't think about session, presentation, and application as separate concerns — your app code just deals with it. TLS (encryption/certificates) is technically "presentation layer" in OSI, but in TCP/IP it's just part of what the application layer does.

**Merge 2 — Bottom layers (L1 + L2 → Network Access):**
OSI separates physical signaling (cables, volts, radio waves) from data framing (MAC addresses, Ethernet frames). TCP/IP says: "I don't care about hardware details — that's the network driver's problem." TCP/IP was designed to run over anything — Ethernet, Wi-Fi, carrier pigeon (RFC 1149, actually exists). So it treats the whole physical+data-link stack as a single "not my problem" layer.

**The middle two layers map 1:1:**
- OSI Transport (L4) = TCP/IP Transport → TCP, UDP
- OSI Network (L3) = TCP/IP Internet → IP, ICMP, routing

### Which layers matter most in DevOps:

**Layer 7 (Application):** This is where you live 80% of the time. HTTP status codes, DNS resolution, TLS certificates, API debugging. When your service returns a 502, that's L7.

**Layer 4 (Transport):** TCP vs UDP, port numbers, load balancers (L4 vs L7 LBs are a real distinction in AWS/GCP). When you can't connect to port 443, you're debugging here.

**Layer 3 (Network):** IP routing, subnets, security groups, VPC peering. When your EC2 instance can't reach another subnet, that's L3.

**Layer 2 (Data Link):** You'll hit this less often, but it shows up in VPCs (MAC addresses), ARP tables, and VLAN configurations in on-prem data centers.

### The grand scheme:

The internet runs on TCP/IP. Nobody implements OSI protocols. But everyone uses OSI vocabulary to describe TCP/IP networks. When an AWS engineer says "we need an L7 load balancer," they're using OSI terminology to describe a TCP/IP component (an ALB that inspects HTTP headers). The OSI model won the language war; TCP/IP won the implementation war.
