# DevOps Learning Log — 2026-6-4

## Q1: What is the difference between shells and kernels? What are they? Why do we have different shells?

### The kernel: the actual operating system

The kernel is the one piece of software that talks directly to your hardware — CPU, RAM, disk, network card. Every program on your computer, without exception, goes through the kernel to do anything real. When your Python script writes to a file, it doesn't talk to the disk itself. It asks the kernel ("hey, write these bytes to this location"), and the kernel handles the hardware interaction. These requests are called **system calls (syscalls)**.

The kernel manages:
- **Processes:** which programs run, how much CPU time each gets, starting/stopping them
- **Memory:** which program gets which chunk of RAM, preventing one program from reading another's memory
- **Filesystems:** reading/writing files on disk
- **Networking:** sending/receiving packets through the network interface
- **Device drivers:** talking to hardware (keyboard, display, USB devices)

On Linux, the kernel is literally a file: `/boot/vmlinuz`. It loads when the machine boots and runs until shutdown. Everything else — your terminal, your browser, Docker, Kubernetes — is a program running *on top of* the kernel.

### The shell: the interface between you and the kernel

A shell is just a program — a regular user-space application — that takes your typed commands, interprets them, and translates them into syscalls that the kernel executes. That's it. It's a translator.

When you type `ls /home`, here's what actually happens:
1. The shell reads your input: `ls /home`
2. It finds the `ls` binary at `/usr/bin/ls`
3. It makes a `fork()` syscall → kernel creates a new process
4. It makes an `exec()` syscall → kernel loads the `ls` binary into that process
5. `ls` makes `opendir()` and `readdir()` syscalls → kernel reads the directory from disk
6. `ls` makes `write()` syscalls → kernel sends the output to your terminal
7. `ls` exits → kernel cleans up the process

You never talk to the kernel directly. The shell does it for you.

### The relationship — the name says it all

Think of a nut. The **kernel** is the core inside — the essential part that does the real work. The **shell** is the hard outer layer — the interface you interact with to reach the kernel. The naming is literal.

```
┌──────────────────────────────────┐
│           USER (you)             │
├──────────────────────────────────┤
│         SHELL (bash, zsh)        │  ← interprets your commands
│         translates to syscalls   │
├──────────────────────────────────┤
│         KERNEL (Linux)           │  ← manages hardware, processes, memory
│         executes syscalls        │
├──────────────────────────────────┤
│         HARDWARE                 │  ← CPU, RAM, disk, NIC
└──────────────────────────────────┘
```

### Why do we have different shells?

Because the shell is just a program, anyone can write a new one. Different shells exist because people disagreed about syntax, features, and what a good command-line experience should feel like.

**sh (Bourne Shell, 1979):**
The original Unix shell. Minimal, no frills. Still the standard for writing portable shell scripts — if you write `#!/bin/sh` at the top of a script, it'll work on basically any Unix system. Most systems still ship it.

**bash (Bourne Again Shell, 1989):**
The GNU project's upgrade to `sh`. Added command history, tab completion, arrays, better scripting syntax. Was the default on Linux and Mac for decades. This is what most "shell scripting" tutorials teach. When someone says "write a bash script," they mean this.

**zsh (Z Shell, 1990):**
Everything bash does, plus better tab completion, plugin support, spelling correction, themeable prompts. Apple switched macOS from bash to zsh as the default in 2019. If you're on a Mac and open Terminal, you're using zsh.

**fish (Friendly Interactive Shell, 2005):**
Designed for usability. Auto-suggestions as you type, syntax highlighting in real-time, sane defaults without configuration. Intentionally breaks compatibility with bash/POSIX syntax — it's not trying to be backward compatible, it's trying to be better for interactive use.

**dash:**
An ultra-minimal, fast shell. Debian/Ubuntu use it as `/bin/sh` instead of bash because it starts faster — matters when the system runs hundreds of shell scripts during boot. You'd never use it interactively, but your system probably uses it behind the scenes.

### Why this matters for DevOps:

**Dockerfiles use `sh`, not `bash`.** Most minimal Docker images (like `alpine`) don't have bash installed — they only have `sh` (or `ash`, a minimal sh-compatible shell). If your `RUN` command uses bash-specific syntax (like `[[ ]]` instead of `[ ]`), it'll fail inside the container. This is a common gotcha.

**Scripts should target `sh` for portability.** If you write a deploy script with `#!/bin/bash` and run it on an Alpine container or a minimal server, bash might not be there. `#!/bin/sh` is safer for scripts that need to run anywhere.

**Your interactive shell is personal preference.** Use zsh or fish for your daily terminal — the autocompletion and quality-of-life features are worth it. But write your scripts for `sh` or `bash` because that's what servers and containers have.

## Q2: Is Fedora a Linux OS?

**Yes — but more precisely, Fedora is a Linux distribution.** It uses the Linux kernel but packages it with its own choices of shell, package manager, desktop environment, and default software.

"Linux" by itself is just the kernel. A **distribution (distro)** bundles the kernel with everything else you need to actually use a computer — a shell (bash), a package manager, system utilities, and optionally a desktop GUI.

Fedora specifically:
- Sponsored by **Red Hat** (owned by IBM)
- Uses the **dnf** package manager (like how Ubuntu uses apt)
- Serves as the upstream testing ground for **RHEL (Red Hat Enterprise Linux)** — features land in Fedora first, get battle-tested, then move into RHEL for enterprise customers
- Ships cutting-edge software (newer kernel versions, latest GNOME desktop)
- Default shell: bash

### The major distro families and why DevOps cares:

**Debian family:** Debian → Ubuntu → Linux Mint
- Package manager: `apt` / `.deb` files
- Ubuntu dominates cloud servers — most EC2 AMIs, Docker base images, and CI runners use Ubuntu
- Docker's default base images (`python:3.12`, `node:20`) are usually Debian-based

**Red Hat family:** Fedora → RHEL → CentOS / Rocky / Alma
- Package manager: `dnf` (formerly `yum`) / `.rpm` files
- RHEL dominates enterprise on-prem — banks, governments, large corporations
- CentOS was the free RHEL clone until Red Hat killed it in 2020; Rocky Linux and AlmaLinux replaced it

**Alpine:**
- Package manager: `apk`
- Tiny (~5MB base image vs ~80MB for Debian)
- The go-to for minimal Docker images (`python:3.12-alpine`)
- Uses `musl` libc instead of `glibc` — this occasionally breaks things

The distro you use daily doesn't matter much. What matters for DevOps is knowing that **your server, your CI runner, and your Docker container might all be different distros** — and their package managers and default tools differ. A script that runs `apt install` won't work on a Fedora/RHEL server that uses `dnf`.

## Q3: Why write scripts on one VM/container and push to another?

**Because the machine you write code on should never be the machine that runs it in production.** The entire DevOps pipeline exists to enforce this separation.

### The problem with writing and running on the same machine:

Say you write a deploy script directly on your production server, edit it there, test it there. What goes wrong:

**1. You have no rollback.**
You edit the script, it breaks production. The previous version? Gone — you overwrote it. If the script lived in Git on a separate machine, you'd `git revert` in seconds.

**2. No review process.**
Nobody else saw your change before it hit production. No code review, no automated tests, no approval. One typo takes the site down.

**3. "Works on my machine" in reverse.**
Your production server has specific packages, env vars, permissions. You start depending on things that only exist on that one server. When you need to rebuild it (and you will — hardware fails, you scale to more servers), you can't reproduce the environment because the setup was never captured anywhere.

**4. Security.**
If you're SSHing into production servers to edit files, every developer needs SSH access to production. That's a massive attack surface. The principle of **least privilege** says: developers write code on their machines, CI/CD pushes it to production, humans never touch prod directly.

### The correct flow:

```
Your laptop          →  Git (GitHub)  →  CI/CD (GitHub Actions)  →  Production
(write & test code)     (store code)     (build, test, deploy)      (run code)
```

Each step is a different machine (or container):

**Your laptop / dev VM:** Write the code, run it locally, test it. This is where your docker-compose.yml runs.

**Git repository:** Code is pushed here. This is the source of truth. Everything deployed to production must come from Git — never from someone's laptop.

**CI/CD server (GitHub Actions, Jenkins, etc.):** An automated system pulls the code from Git, runs tests, builds a Docker image, and pushes it to production. No human decision-making in this step — it's a pipeline.

**Production server/cluster:** Runs the built artifact (Docker image, binary, etc.). Nobody SSHs into this to edit files. If something needs to change, you change it in Git, and the pipeline redeploys.

### Why separate containers/VMs for each stage:

**Isolation of concerns.** Your dev machine has your IDE, debugging tools, test data, personal files. Production has only what's needed to run the app — nothing extra. Mixing them creates bloated, insecure, unreproducible environments.

**Reproducibility.** If production is a Docker container built from a Dockerfile in Git, you can rebuild it identically anytime, anywhere. If production is a server someone hand-configured over 3 years, you can't.

**Blast radius.** Your test script has a bug that deletes a directory. On your dev VM? Annoying. On production? Catastrophe. Separate machines mean a mistake in one environment can't affect another.

### The exception — when you DO write directly on the server:

Emergency hotfixes. Production is down, the fix is a one-line change, and the pipeline takes 20 minutes. You SSH in, make the fix, get the site back up — then immediately commit the same fix to Git so the pipeline picks it up. This should be rare and uncomfortable. If you're doing it regularly, your pipeline is too slow.

## Q4: Check all Vagrant VMs globally and destroy them (pipe command)

```bash
vagrant global-status | awk '/running|poweroff|saved/{print $1}' | xargs -I {} vagrant destroy {} -f
```

### What each part does:

**`vagrant global-status`** — lists every Vagrant VM on your machine regardless of which directory you're in. Outputs something like:

```
id       name    provider   state    directory
------------------------------------------------------------------------
a1b2c3d  web01   virtualbox running  /home/tosin/devops/project1
e4f5g6h  db01    virtualbox running  /home/tosin/devops/project2
i7j8k9l  app01   virtualbox saved    /home/tosin/devops/project3
```

**`awk '/running|poweroff|saved/{print $1}'`** — filters to lines containing "running", "poweroff", or "saved" (i.e., VMs that exist), then prints only the first column (the VM id). Output: `a1b2c3d`, `e4f5g6h`, `i7j8k9l`.

**`xargs -I {} vagrant destroy {} -f`** — takes each id and runs `vagrant destroy <id> -f` on it. The `-f` flag forces destruction without asking "are you sure?"

### Other useful variations:

```bash
# Just list all VMs (no destruction)
vagrant global-status

# Prune stale entries (VMs that no longer exist on disk)
vagrant global-status --prune

# Destroy only running VMs
vagrant global-status | awk '/running/{print $1}' | xargs -I {} vagrant destroy {} -f

# Halt (stop) all instead of destroying
vagrant global-status | awk '/running/{print $1}' | xargs -I {} vagrant halt {}
```

## Q5: What are `awk` and `xargs`?

### awk — a line-by-line text processor

`awk` reads input line by line, splits each line into columns (by whitespace), and lets you filter and pick which columns to print.

**The basics:**

Given this input:
```
id       name    state    directory
a1b2c3d  web01   running  /home/tosin/project1
e4f5g6h  db01    poweroff /home/tosin/project2
i7j8k9l  app01   running  /home/tosin/project3
```

```bash
# Print the whole line
awk '{print}' 

# Print first column only ($1)
awk '{print $1}'
# Output: id, a1b2c3d, e4f5g6h, i7j8k9l

# Print first and third columns
awk '{print $1, $3}'
# Output: id state, a1b2c3d running, e4f5g6h poweroff, i7j8k9l running

# Filter: only lines containing "running", then print first column
awk '/running/{print $1}'
# Output: a1b2c3d, i7j8k9l

# Filter: only lines where column 3 equals "running"
awk '$3 == "running" {print $1}'
# Output: a1b2c3d, i7j8k9l
```

**How awk splits columns:**
`$0` = the entire line
`$1` = first column, `$2` = second, `$3` = third, etc.
By default, columns are split on whitespace (spaces or tabs). You can change the delimiter with `-F`:

```bash
# Split on colon (useful for /etc/passwd)
awk -F: '{print $1}' /etc/passwd
# Output: root, daemon, tosin, ...
```

**The pattern:** `awk '/pattern/{action}'`
- `/pattern/` is a regex filter — only matching lines get processed
- `{action}` is what to do with matching lines — usually `print` specific columns
- You can skip either part: `awk '{print $1}'` (no filter, all lines) or `awk '/error/'` (no action, prints whole matching line)

### xargs — turn input lines into command arguments

`xargs` takes a list of items from stdin and runs a command once for each item. It solves the problem: "I have a list of things, and I want to do something to each one."

**Without xargs (doesn't work):**
```bash
# This DOESN'T work — vagrant destroy doesn't read from stdin
echo "a1b2c3d" | vagrant destroy
```

**With xargs (works):**
```bash
# -I {} means "replace {} with each input item"
echo "a1b2c3d" | xargs -I {} vagrant destroy {} -f
# Runs: vagrant destroy a1b2c3d -f
```

**Multiple items:**
```bash
echo -e "a1b2c3d\ne4f5g6h\ni7j8k9l" | xargs -I {} vagrant destroy {} -f
# Runs three commands:
#   vagrant destroy a1b2c3d -f
#   vagrant destroy e4f5g6h -f
#   vagrant destroy i7j8k9l -f
```

**Real-world examples:**

```bash
# Delete all .log files in current directory
find . -name "*.log" | xargs rm

# Stop all running Docker containers
docker ps -q | xargs docker stop

# Kill all processes matching "node"
pgrep node | xargs kill

# Pull all git repos in subdirectories
ls -d */ | xargs -I {} git -C {} pull
```

### The pipe pattern: `produce | filter | act`

This is the Unix philosophy in action. Each tool does one thing:
1. **Produce** — a command generates output (`vagrant global-status`, `find`, `docker ps`)
2. **Filter** — `awk`/`grep`/`sed` narrows it to what you care about
3. **Act** — `xargs` turns the filtered output into commands

```bash
vagrant global-status | awk '/running/{print $1}' | xargs -I {} vagrant destroy {} -f
│                       │                            │
│ PRODUCE               │ FILTER                     │ ACT
│ (list all VMs)        │ (grab IDs of running ones) │ (destroy each one)
```

This three-part pattern is the backbone of shell one-liners in DevOps.

## Q6: Why does my Fedora VM take so long to receive an IP address?

**Multiple things are stacking up, but the most likely culprit is `v.ssh_info_public = true` combined with how Fedora's NetworkManager handles multiple interfaces.**

### What happens during `vagrant up` before you get a prompt:

1. VMware creates the VM and boots it
2. The VM's primary NAT adapter tries to get an IP via DHCP from VMware's built-in DHCP server
3. The private_network adapter (`192.168.56.x`) gets configured
4. Vagrant repeatedly polls the VM: "do you have an IP yet? can I SSH in?"
5. Once SSH works, Vagrant runs the provisioning shell script

The delay is almost certainly in steps 2-4. Here's why:

### Cause 1: `v.ssh_info_public = true`

This setting tells Vagrant to wait for the VM to report a publicly accessible IP rather than using VMware tools to detect the IP internally. This adds a polling loop where Vagrant keeps asking "what's your IP?" and waiting for a response. On a fresh boot with a new box, the VM hasn't configured its network yet, so Vagrant sits there retrying.

### Cause 2: Fedora's NetworkManager waits on ALL interfaces

Fedora uses NetworkManager, which by default waits for network connectivity on every interface before considering the network "up." Your VM has two interfaces — the NAT adapter and the private_network adapter. Both need to come up. The private_network adapter gets configured after boot by Vagrant via SSH, creating a chicken-and-egg delay: Vagrant needs SSH to configure the network, but the network needs to be up for SSH.

### Cause 3: Fedora 35 is end-of-life

Fedora 35 EOL'd in December 2022. This won't directly slow IP assignment, but during provisioning, `yum update` will try to reach repos that may be moved to `archives.fedoraproject.org` or unreachable. This can make the overall `vagrant up` feel even slower after the IP is assigned — yum hangs trying to contact dead mirrors.

Your Vagrantfile actually mitigates this by moving the update repos to `/tmp/` before running `yum update` — but `yum update` with no valid repos will still take time to figure out there's nothing to do.

### Cause 4: Three Fedora VMs sequentially

Vagrant brings up VMs sequentially by default — scriptbox, then web01, then web02, then web03. Each one goes through the full boot → IP → provision cycle. If each takes 3-4 minutes, you're looking at 12-16 minutes total.

### Things to try:

```ruby
# 1. Remove ssh_info_public if you don't need it — it adds polling delay
v.ssh_info_public = true  # ← try removing this line

# 2. Add a boot timeout so Vagrant doesn't wait forever
scriptbox.vm.boot_timeout = 600  # seconds

# 3. Bring VMs up in parallel (if independent)
# From the command line:
# vagrant up --parallel
```

### Comparison: why web03 (Ubuntu) is probably faster

Your `web03` uses `spox/ubuntu-arm` and has no provisioning script. Ubuntu uses `systemd-networkd` (lighter than NetworkManager) and skips the whole yum update step. It likely gets its IP and becomes SSH-ready much faster.

## Q7: Is CentOS gone?

**Yes. CentOS as you knew it is dead.** Red Hat killed it in December 2020.

### What happened:

CentOS was a free, community-maintained clone of RHEL (Red Hat Enterprise Linux). Same source code, same binaries, same stability — just without the Red Hat support contract. Companies ran CentOS in production to get RHEL quality for free. It was massive — one of the most widely deployed server OSes in the world.

In December 2020, Red Hat announced they were shifting CentOS from a downstream rebuild of RHEL (stable, released after RHEL) to **CentOS Stream** — an upstream rolling-release distro that sits *before* RHEL. Think of it as a beta channel for RHEL rather than a free copy of it.

```
Before:  RHEL releases → CentOS rebuilds it (stable, identical)
After:   CentOS Stream (testing) → feeds into RHEL (stable)
```

This killed the value proposition. The whole point of CentOS was "RHEL without paying." CentOS Stream is "pre-RHEL that might break."

### The community response:

Two projects immediately forked CentOS to fill the gap:

**Rocky Linux** — founded by Gregory Kurtzer, who originally co-founded CentOS. Same mission: free 1:1 RHEL rebuild.

**AlmaLinux** — backed by CloudLinux (a hosting company). Also a free 1:1 RHEL rebuild.

Both are drop-in replacements for CentOS. Same packages, same `dnf`, same everything. AlmaLinux is what we're using in your Vagrantfile because it has well-maintained ARM64 Vagrant boxes.

### Timeline:
- CentOS 8 EOL: December 31, 2021 (originally promised support until 2029 — Red Hat cut it short)
- CentOS 7 EOL: June 30, 2024 (this was the last "real" CentOS)
- CentOS Stream: still exists, but serves a different purpose

### Why this matters for DevOps:

If you see CentOS in job descriptions, tutorials, or existing infrastructure, it means one of three things: they haven't migrated yet (legacy), they mean CentOS Stream (different thing), or they really mean Rocky/Alma and haven't updated the name. When someone says "CentOS-like" in 2026, they mean Rocky or Alma.
