# DevOps Learning Log — 2026-6-1

## Q1: What is the cost difference between setting up a monolith vs microservices, all things being equal?

**Microservices are significantly more expensive to set up and run. A monolith is cheaper at every stage until you hit a specific set of scaling or organizational problems that force the split.**

### Infrastructure costs:

**Monolith:**
- 1 server (or a few for redundancy) — say 2 EC2 instances behind a load balancer
- 1 database
- 1 deployment pipeline
- Estimated monthly: ~$100-500 for a small-to-medium app on AWS

**Microservices (same app, split into 5-8 services):**
- Each service needs its own compute (containers/pods), often with a minimum of 2 replicas for availability — that's 10-16 containers minimum
- You now need Kubernetes or ECS to orchestrate them — the control plane alone costs money (EKS is $75/month just for the cluster, before any workloads)
- Each service might need its own database (the "database per service" pattern) — multiply your RDS bill by 5-8
- A service mesh (Istio, Linkerd) or at minimum an API gateway to handle inter-service communication
- A container registry to store all the images
- Centralized logging (you can't just SSH in and read one log file anymore) — ELK stack or Datadog, which can easily cost $500-2000/month
- Distributed tracing (Jaeger, Datadog APT) — because when a request touches 5 services, you need to trace it across all of them
- Estimated monthly: ~$1,000-5,000+ for the same app

### People costs (this is where it really hurts):

**Monolith:**
- 1 developer can understand and deploy the whole thing
- 1 CI/CD pipeline to maintain
- Debugging: read the stack trace, it's all in one process

**Microservices:**
- Each service needs its own CI/CD pipeline — that's 5-8 pipelines to maintain
- You need a platform/DevOps engineer just to manage the infrastructure (Kubernetes, service mesh, monitoring)
- Debugging is harder: a request fails, but which of the 5 services it touched caused the failure? You need distributed tracing set up correctly
- Contract management: services talk to each other via APIs. When Service A changes its API, does it break Services B, C, and D? You need contract testing
- You need engineers who understand distributed systems — network partitions, eventual consistency, circuit breakers, retry logic. These people cost more

### The hidden costs of microservices people don't talk about:

**Network latency:** A function call inside a monolith takes nanoseconds. The same call between two microservices goes over the network — milliseconds. Multiply that across a request that touches 5 services and you've added real latency.

**Data consistency:** In a monolith, you can wrap 3 database writes in a single transaction. Across microservices, you need sagas or eventual consistency patterns. This is genuinely hard engineering.

**Testing complexity:** Integration testing a monolith = start the app, run tests. Integration testing microservices = start all 5-8 services, their databases, the service mesh... you basically need a mini production environment.

### When microservices are worth the cost:

- **Organizational scaling:** You have 50+ engineers and they're stepping on each other in the monolith codebase. Different teams can own and deploy different services independently.
- **Independent scaling:** One part of your app gets 100x more traffic than the rest. You can scale just that service instead of scaling everything.
- **Technology diversity:** One service needs Python for ML, another needs Go for performance. A monolith locks you into one stack.
- **Independent deployment:** You need to ship one feature without risking the whole app. Each service deploys on its own schedule.

### The right mental model:

A monolith is a studio apartment — cheap, simple, everything in one place. Microservices are a house with separate rooms — more expensive, more to maintain, but you need them when your family grows. Don't buy a house for one person.

## Q2: Structure of a docker-compose.yml file — 5 containers (Java, Node, MongoDB, Postgres, Python)

### The full file:

```yaml
# The top-level keys are: services, volumes, networks
# That's it — every Compose file is just these three sections

services:

  # ─── SERVICE 1: Java backend (Spring Boot API) ───
  java-api:
    build:                          # Build from a Dockerfile instead of pulling an image
      context: ./java-api           # Path to the directory containing the Dockerfile
      dockerfile: Dockerfile        # Name of the Dockerfile (optional if it's just "Dockerfile")
    image: myapp/java-api:latest    # Tag the built image with this name
    ports:
      - "8080:8080"                 # HOST_PORT:CONTAINER_PORT — expose to your machine
    environment:                    # Env vars injected into the container
      - SPRING_DATASOURCE_URL=jdbc:postgresql://postgres-db:5432/appdb
      - SPRING_DATASOURCE_USERNAME=appuser
      - SPRING_DATASOURCE_PASSWORD=secret123
    depends_on:                     # Start these services first
      - postgres-db
    networks:                       # Which networks this container joins
      - backend
    restart: unless-stopped         # Restart policy: always restart unless you explicitly stop it

  # ─── SERVICE 2: Node.js frontend/BFF ───
  node-app:
    build:
      context: ./node-app
    ports:
      - "3000:3000"
    environment:
      - MONGO_URI=mongodb://mongo-db:27017/analytics
      - JAVA_API_URL=http://java-api:8080
    depends_on:
      - mongo-db
      - java-api
    volumes:
      - ./node-app/src:/app/src     # BIND MOUNT: sync local code into container (for dev hot-reload)
    networks:
      - backend
      - frontend
    restart: unless-stopped

  # ─── SERVICE 3: Python worker (background jobs / ML) ───
  python-worker:
    build:
      context: ./python-worker
    environment:
      - DATABASE_URL=postgresql://appuser:secret123@postgres-db:5432/appdb
      - MONGO_URI=mongodb://mongo-db:27017/analytics
    depends_on:
      - postgres-db
      - mongo-db
    networks:
      - backend
    restart: unless-stopped
    # No ports — this isn't a web server, it's a background worker

  # ─── SERVICE 4: PostgreSQL (relational data) ───
  postgres-db:
    image: postgres:16              # Pull directly from Docker Hub, no build needed
    environment:
      - POSTGRES_DB=appdb
      - POSTGRES_USER=appuser
      - POSTGRES_PASSWORD=secret123
    ports:
      - "5432:5432"                 # Expose so you can connect from your host (e.g., pgAdmin)
    volumes:
      - pgdata:/var/lib/postgresql/data   # NAMED VOLUME: persist data across container restarts
    networks:
      - backend
    restart: unless-stopped

  # ─── SERVICE 5: MongoDB (document data / analytics) ───
  mongo-db:
    image: mongo:7
    environment:
      - MONGO_INITDB_DATABASE=analytics
    ports:
      - "27017:27017"
    volumes:
      - mongodata:/data/db
    networks:
      - backend
    restart: unless-stopped

# ─── VOLUMES: named volumes persist data beyond container lifecycle ───
volumes:
  pgdata:         # Postgres data survives "docker compose down"
  mongodata:      # Mongo data survives "docker compose down"
  # Note: "docker compose down -v" DELETES these volumes — careful

# ─── NETWORKS: isolate communication between groups of services ───
networks:
  backend:        # All services that need to talk to each other
  frontend:       # Only services that face the user

## Q3: Why doesn't Docker tell you about Dockerfile syntax errors before you run `docker compose up`?

**Because Docker doesn't validate Dockerfiles ahead of time. It only reads them at build time.**

### The core issue: Docker has no "compile" step.

When you run `docker compose up`, the sequence is:
1. Parse `docker-compose.yml` (YAML syntax errors ARE caught here)
2. For each service with `build:`, read the Dockerfile and execute it line by line
3. A syntax error (like an unclosed bracket) only surfaces when Docker hits that specific line during the build

There's no pre-flight check. Docker doesn't scan the whole Dockerfile for syntax before starting. It processes instructions sequentially and fails at the broken line — often with a cryptic error message that doesn't say "you forgot to close a bracket."

### Why Docker works this way:

Dockerfiles aren't a programming language with a formal grammar. They're a sequence of shell commands wrapped in Docker instructions (`RUN`, `COPY`, `CMD`, etc.). Docker passes `RUN` contents directly to `/bin/sh` inside the container. So an unclosed bracket in a `RUN` command is a shell syntax error, not a Docker syntax error — Docker can't know it's wrong until bash tries to execute it.

### How to catch these errors earlier:

**1. IDE linting (best solution):**
Install the Docker extension in VS Code. It highlights Dockerfile syntax errors in real-time — red squiggles before you ever run anything. This is the equivalent of a spell-checker for Dockerfiles.

**2. `docker build` before `docker compose up`:**
```bash
docker build -t test ./java-api
```
This builds just that one service's image. Faster feedback loop than running the whole Compose stack and waiting for it to fail.

**3. Hadolint (Dockerfile linter):**
```bash
hadolint ./java-api/Dockerfile
```
Catches syntax errors AND bad practices (running as root, not pinning package versions, etc.).

**4. Multi-stage builds surface errors earlier:**
If your Dockerfile has a compilation step (like `mvn package` for Java), the build fails at that stage — before the container ever tries to run.
```

### The anatomy — what each top-level key does:

**`services`** — the heart of the file. Each child key is a container. Each service can either `build` from a local Dockerfile or pull a pre-built `image` from a registry.

**`volumes`** — named storage that persists beyond the container's lifecycle. Without this, your database data disappears every time you run `docker compose down`. Two types show up in this file:
- **Named volumes** (`pgdata:/var/lib/postgresql/data`) — Docker manages the storage location. Data persists.
- **Bind mounts** (`./node-app/src:/app/src`) — maps a directory on your machine directly into the container. Used for development so code changes reflect immediately without rebuilding.

**`networks`** — virtual networks that control which containers can talk to each other. In this example, `postgres-db` is on the `backend` network but NOT on `frontend`, so a frontend-only container couldn't reach it directly. If you don't define networks, Compose puts everything on one default network.

### Key concepts in the service definitions:

**`ports: "HOST:CONTAINER"`** — maps a port on your machine to a port inside the container. `"8080:8080"` means localhost:8080 on your Mac hits port 8080 inside the container. The python-worker has NO ports because it's a background process, not a web server.

**`depends_on`** — controls startup order. `java-api` depends on `postgres-db`, so Postgres starts first. But this only waits for the container to start, NOT for the database to be ready to accept connections. In practice you often need a health check or a wait script.

**`environment`** — env vars injected into the container. Notice the hostnames: `postgres-db:5432`, `mongo-db:27017`, `java-api:8080`. These are the **service names** from this file — Compose creates a DNS entry for each service name so containers find each other by name, not IP.

**`restart: unless-stopped`** — container auto-restarts if it crashes, but stays down if you explicitly stop it. Other options: `always`, `on-failure`, `no`.

### How the containers find each other (DNS):

This is the key networking concept. When `java-api` connects to `postgres-db:5432`, it's using DNS. Compose runs an embedded DNS server inside the network. Each service name becomes a hostname that resolves to that container's IP. This is exactly the same concept as the `nslookup` and virtual hosting you learned earlier — just inside Docker's private network.
