# DevOps Learning Log — 2026-8-29

## Q1: What can you do with an AMI, and does it propagate changes to running servers?

An AMI (Amazon Machine Image) is a template for launching EC2 instances — it bundles the OS, installed software, and configuration, frozen at a point in time.

### What you can do with an AMI

- Launch new instances from it (the core use case)
- Copy it to another AWS region
- Share it with another AWS account (private share, or publish it on the Marketplace)
- Use it as the source image in an Auto Scaling Group's launch template
- Deregister it and keep/delete the underlying EBS snapshot as a backup

### Why copy an AMI to another region

- **Disaster recovery** — if the primary region goes down, you can spin up in another region fast
- **Latency** — serve users closer to them (e.g. an Asia region instead of us-east-1)
- **Compliance** — some data must physically reside in a specific region
- **Migration** — moving a whole footprint from one region to another over time

### The propagation misconception (the important part)

An AMI is a **snapshot, not a live connection** — like a photograph, not a video feed. Once an instance launches from an AMI, it becomes fully independent. Changes made on one running instance (new code, config edits, installed packages) do **not** flow back into the AMI, and do not propagate to other instances launched from the same AMI. Every instance lives its own life after launch.

### How fleets actually stay in sync — two philosophies

1. **Mutable approach** — push changes to all running servers after the fact using config management (Ansible, Chef, Puppet, SSM Run Command). The AMI stays static; the fleet gets updated in place.
2. **Immutable approach ("golden AMI" pattern)** — never touch running servers directly. Code change → CI/CD pipeline builds a *new* AMI (often via Packer) → new AMI becomes the launch template's source → Auto Scaling Group does a rolling replacement, terminating old instances and launching fresh ones from the new AMI.

### Why this matters for DevOps

The immutable/golden-AMI pattern is the backbone of a lot of production AWS CI/CD pipelines — it's the actual mechanism that connects "I built a new AMI" to "my fleet is now running the new code," without ever SSHing into a live server to patch it.

## Q2: What are launch templates?

A launch template is a saved, **versioned** blueprint for launching EC2 instances — instead of manually specifying AMI, instance type, security groups, etc. every time, you define the config once and reference it.

### What it bundles

- AMI ID
- Instance type
- Key pair
- Security groups
- Subnet / networking config
- IAM instance profile
- Storage (EBS volume size, type, encryption)
- User data (startup script run on first boot)
- Tags

### The versioning is the whole point

Launch templates version like commits:

```
Launch Template: my-app-server
  Version 1: AMI-abc123, t3.small
  Version 2: AMI-def456, t3.small   ← new AMI from CI/CD pipeline
  Version 3: AMI-def456, t3.medium  ← bumped instance size
```

This is the missing link in the golden-AMI pipeline:

```
Code change → CI/CD builds new AMI (Packer)
  → CI/CD creates a new launch template VERSION pointing at that AMI
  → Auto Scaling Group updated to use the new launch template version
  → ASG does a rolling replacement
```

The ASG never needs to know *how* to configure an instance — it just launches from "template X, version Y." That separation is what keeps automated deployment pipelines clean.

### Launch template vs. launch configuration (legacy)

| | Launch Configuration (legacy) | Launch Template (current) |
|---|---|---|
| Versioning | None — immutable, must create a new one | Yes — versioned, can set a default |
| Usable standalone (`run-instances`) | No, ASG only | Yes |
| Mixed instance types / Spot + On-Demand | No | Yes |
| AWS's recommendation | Deprecated path | Use this |

### User data — the sneaky powerful part

User data is a script that runs automatically the first time an instance boots. Even with a static AMI, user data can pull the latest code, fetch secrets, or register the instance with a service on boot — a hybrid between "frozen AMI" and "always fresh at launch." Some teams lean on this instead of constantly rebuilding AMIs.

### Where you'll see this in DevOps

Launch templates are the config object that Auto Scaling Groups, EC2 Fleet, and Spot Fleet all reference — understanding them is a prerequisite for understanding rolling deployments and instance refresh.

## Q3: CloudWatch — Logs vs. Metrics vs. Events, and is there better UX?

### The core distinction

| | Question it answers | What it looks like | Example |
|---|---|---|---|
| **Logs** | "What exactly happened?" | Raw text/JSON, timestamped, high detail | `2026-08-29 14:02:11 ERROR DB connection timeout` |
| **Metrics** | "How much / how many, over time?" | Numeric time-series data points | CPUUtilization: 73% at 14:02, 75% at 14:03 |
| **Events** | "Something happened — react to it" | A signal used to trigger automation | "EC2 instance state changed to stopped" |

The hierarchy: **logs are raw evidence, metrics are aggregated numbers (often derived from logs, sometimes emitted natively), and events/alarms are the automation layer sitting on top of metrics, watching for thresholds and reacting.**

Same underlying situation, seen three ways:

- **Log:** `[ERROR] Payment API returned 500 for order #4471`
- **Metric:** `5xxErrorCount` jumps from 2 to 47 in one minute
- **Event:** CloudWatch Alarm (watching that metric) fires a state-change event → triggers SNS → pages you

### Is there better UX than the native console?

Yes — this is a common complaint, and the native console is weakest at *correlating* logs and metrics together.

- **CloudWatch Logs Insights** — still native AWS, but a much better query interface than tailing raw log groups; a lightweight query language over logs.
- **Grafana** (self-hosted or AWS Managed) — the most common upgrade path for metrics dashboards, using CloudWatch as a data source.
- **Datadog / New Relic / Honeycomb** — third-party observability platforms that ingest CloudWatch logs/metrics and give correlated views — click an error spike on a graph, jump straight to the logs from that moment. This correlation is what native CloudWatch is genuinely weak at.
- **OpenSearch** (via CloudWatch Logs subscription) — teams needing serious log search/filtering often stream logs into OpenSearch instead.

### Why this matters for DevOps

CloudWatch is usually the *collection* layer — AWS is good at getting the data in — and teams bolt on a better *visualization/correlation* layer once they outgrow the native console. Knowing this pattern helps when evaluating "do we need Datadog" conversations.
