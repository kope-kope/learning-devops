# DevOps Learning Log — 2026-5-29

## Q1: Does Claude Cowork use Docker to run scripts?

**No — Cowork uses a lightweight VM, not Docker.**

When I run a script (via the bash tool), it executes inside a dedicated **Linux virtual machine** isolated from your Mac by Apple's Virtualization.framework (Hyper-V on Windows). This is a real VM with its own kernel, not a Docker container.

### Why a VM instead of Docker?

Docker containers share the host kernel — they're process-level isolation using Linux namespaces and cgroups. A VM runs its own kernel entirely, which provides a stronger security boundary. Anthropic chose VMs so that even if the AI ran something malicious inside the sandbox, it couldn't escape to the host OS. Docker escape vulnerabilities exist; VM escape is much harder.

### What the sandbox looks like:

- Ubuntu 22 Linux environment
- Python, Node.js, and common CLI tools preinstalled
- Connected folders mounted in read/write (e.g., `/sessions/.../mnt/learning-logs/`)
- Network access is allowlisted (not open internet)
- Each bash call is independent — no state carries between calls

### Where Docker DOES show up in Anthropic's stack:

- **Computer use** (browser/desktop automation): reference implementation runs inside a Docker container
- **Claude Code devcontainers**: Claude Code (the CLI tool) can run inside Docker dev containers
- **Managed agents**: Anthropic's cloud infrastructure uses containers for scaling agent sessions server-side

### The DevOps takeaway:

This is a textbook example of the **VM vs container** tradeoff. Containers are lightweight and fast but share the host kernel (weaker isolation). VMs are heavier but have a hard security boundary. Cowork chose VMs because the threat model (untrusted AI-generated code on a user's personal machine) demands the stronger guarantee.

## Q2: Why would a software developer use Docker Compose in the real world?

**Because real apps aren't one container — they're 3-10 containers that need to talk to each other.**

### The problem Compose solves:

Say you're building a web app. You need:
- A Python/Node backend
- A PostgreSQL database
- A Redis cache
- Maybe Nginx as a reverse proxy

Without Compose, you'd run each container manually:
```bash
docker run -d --name db -e POSTGRES_PASSWORD=secret postgres:15
docker run -d --name cache redis:7
docker run -d --name app --link db --link cache -p 8000:8000 myapp
docker run -d --name nginx --link app -p 80:80 mynginx
```

That's 4 commands with flags you have to remember, type correctly, and run in the right order. Now imagine tearing it all down and rebuilding it 20 times a day during development.

### What Compose does:

One `docker-compose.yml` file declares everything:

```yaml
services:
  app:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - db
      - cache
    environment:
      - DATABASE_URL=postgresql://user:secret@db:5432/myapp

  db:
    image: postgres:15
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - pgdata:/var/lib/postgresql/data

  cache:
    image: redis:7

  nginx:
    image: nginx
    ports:
      - "80:80"
    depends_on:
      - app

volumes:
  pgdata:
```

Then: `docker compose up` — everything starts. `docker compose down` — everything stops. One command.

### Real-world use cases:

**1. Local development (the #1 use case)**
"Clone the repo, run `docker compose up`, the entire app works." New developer onboarding goes from 2 days of installing dependencies to 5 minutes. Everyone runs the exact same versions of Postgres, Redis, etc. — no more "works on my machine."

**2. Running the test suite**
CI pipelines use Compose to spin up the app + its dependencies, run tests, then tear everything down. The test environment is identical every time.

**3. Local simulation of production**
You can approximate your production architecture locally — app server, database, cache, message queue, worker processes — all in one Compose file. Not identical to prod (no load balancer, no replication), but close enough to catch most integration bugs.

**4. Running third-party tools**
Need to run Grafana + Prometheus for monitoring? There's a Compose file for that. Need Elasticsearch + Kibana for log analysis? Compose file. The open-source ecosystem distributes Compose files the way it used to distribute install scripts.

### What Compose is NOT for:

**Production deployments.** Compose runs everything on one machine. In production you need containers spread across multiple machines with health checks, auto-restart, scaling, rolling deploys. That's what Kubernetes, Docker Swarm, or ECS handle. Compose is a development/testing tool.

## Q3: Why can't you run Compose (one machine) in production? What's actually wrong with it?

**You can — for small stuff. The real answer is: one machine is a single point of failure.**

### Nothing is technically wrong with Compose in production for small apps.

If you're running a personal blog or an internal tool with 50 users, Compose on a single server is fine. Plenty of people do it. The problem is what happens when things go wrong or when you need to grow.

### The actual problems with one machine in production:

**1. The machine dies, everything dies.**
Your server's disk fails, the power supply blows, AWS has an AZ outage — your app, your database, your cache, everything is gone simultaneously. There's no second machine to pick up the work. With Kubernetes/ECS, if one node dies, your containers automatically restart on a different node. Compose has no concept of "another machine."

**2. No horizontal scaling.**
Traffic spikes and your app needs 10 instances instead of 2? Compose can do `scale: 10` on one machine, but one machine has finite CPU and RAM. Eventually you hit the ceiling. Real scaling means adding more machines. Compose can't distribute containers across machines — it only knows about the one it's running on.

**3. No rolling deploys.**
You push a new version of your app. With Compose, you do `docker compose up -d --build` — it stops the old container, builds the new image, starts the new container. During that window (could be seconds to minutes), your app is down. Kubernetes does rolling deploys — it starts new containers, waits for them to pass health checks, then drains old ones. Zero downtime.

**4. No self-healing.**
Your app container crashes at 3am. Compose has `restart: always`, which restarts it — but only on the same machine. If the crash is caused by a resource exhaustion issue on that machine (disk full, OOM), restarting on the same machine doesn't help. Orchestrators can reschedule to a healthy machine.

**5. Resource contention.**
Your database and your app compete for the same CPU and RAM. Under load, the app starves the database (or vice versa). In a multi-machine setup, the database runs on dedicated hardware with guaranteed resources.

### The spectrum in practice:

| Setup | When it makes sense |
|-------|-------------------|
| Compose on 1 server | Side projects, internal tools, <100 users |
| Compose + managed DB (e.g., RDS) | Small SaaS, <1000 users. DB is on separate infra so you don't lose data if the app server dies |
| Kubernetes / ECS | Anything that needs uptime guarantees, scaling, or multi-team deployments |

### The real-world middle ground:

Many startups start with Compose on a single server + a managed database (AWS RDS, Cloud SQL). That way your app containers can die and restart without losing data. You only move to Kubernetes when you need multi-machine scaling or zero-downtime deploys. Jumping straight to Kubernetes for a small app is overengineering.
