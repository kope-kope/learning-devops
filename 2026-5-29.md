# DevOps Learning Log — 2026-5-29

## Q1: Why can't you run Compose (one machine) in production? What's actually wrong with it?

**You can — for small stuff. The real answer is: one machine is a single point of failure.**

Nothing is technically wrong with Compose in production for a personal blog or internal tool with 50 users. The problems show up when things go wrong or when you need to grow:

**1. The machine dies, everything dies.**
Server disk fails, AZ outage — app, database, cache all gone simultaneously. Kubernetes auto-restarts containers on a different node. Compose has no concept of "another machine."

**2. No horizontal scaling.**
One machine has finite CPU and RAM. Compose can't distribute containers across machines.

**3. No zero-downtime deploys.**
Compose stops old container → builds new one → starts it. During that gap, app is down. Kubernetes does rolling deploys — starts new containers, health-checks them, then drains old ones.

**4. No self-healing across machines.**
`restart: always` only restarts on the same machine. If the machine itself is the problem (disk full, OOM), restarting locally doesn't help.

**5. Resource contention.**
Database and app compete for the same CPU/RAM on one box.

### The real-world middle ground:

| Setup | When it makes sense |
|-------|-------------------|
| Compose on 1 server | Side projects, internal tools, <100 users |
| Compose + managed DB (e.g., RDS) | Small SaaS, <1000 users |
| Kubernetes / ECS | Uptime guarantees, scaling, multi-team |

Most startups start with Compose + managed DB, then move to K8s when they actually need multi-machine scaling. Jumping straight to Kubernetes for a small app is overengineering.
