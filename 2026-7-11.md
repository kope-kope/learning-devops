# DevOps Learning Log — 2026-7-11

## Q1: chmod — file permissions in Linux

### What chmod does:

`chmod` (change mode) sets who can **read**, **write**, or **execute** a file. Every file in Linux has three permission groups:

- **Owner (u)** — the user who owns the file
- **Group (g)** — users in the file's group
- **Others (o)** — everyone else

Each group gets three permissions:

| Permission | Letter | Number | Meaning |
|-----------|--------|--------|---------|
| Read | r | 4 | View file contents / list directory |
| Write | w | 2 | Modify file / add/delete files in directory |
| Execute | x | 1 | Run as a program / enter directory |

### The number system (most common):

Each permission group gets a single digit (0-7) by adding the permission numbers:

```
r (4) + w (2) + x (1) = 7  → full access
r (4) + w (2)          = 6  → read + write
r (4) +          x (1) = 5  → read + execute
r (4)                  = 4  → read only
                         0  → no access
```

Three digits = owner, group, others:

```bash
chmod 755 script.sh
#     ^^^
#     │││
#     ││└─ others: 5 (r-x) → can read and execute
#     │└── group:  5 (r-x) → can read and execute
#     └─── owner:  7 (rwx) → full access
```

### Common permission sets:

```bash
chmod 755 script.sh    # Standard for scripts/executables
                        # Owner: rwx, everyone else: r-x

chmod 644 config.txt   # Standard for regular files
                        # Owner: rw, everyone else: read only

chmod 600 id_rsa       # SSH private keys — owner only
                        # Owner: rw, everyone else: no access

chmod 777 file         # NEVER do this in production
                        # Everyone can read, write, execute — security nightmare

chmod 700 dir/         # Private directory — only owner can enter
```

### The letter system (when you want to add/remove one permission):

```bash
chmod +x script.sh     # Add execute permission for everyone
chmod u+x script.sh    # Add execute for owner only
chmod g-w file.txt     # Remove write from group
chmod o-rwx secret     # Remove all permissions from others
chmod u+rw,g+r file    # Owner gets rw, group gets r
```

### Deep dive: what does `chmod +x` actually do?

**`chmod +x script.sh` adds execute permission to ALL three groups (owner, group, others).**

Let's trace it. Say your file starts at `644`:

```
Before: -rw-r--r--  (644)
         ^^^  owner: rw-  (read, write, no execute)
            ^^^  group: r--  (read only)
               ^^^  others: r--  (read only)

chmod +x script.sh

After:  -rwxr-xr-x  (755)
         ^^^  owner: rwx  (added x)
            ^^^  group: r-x  (added x)
               ^^^  others: r-x  (added x)
```

The `+x` means "add execute to whoever currently has permissions." It doesn't touch read or write — it only flips the execute bit on. The `+` means add, the `x` means execute. No letter before `+x` means apply to all groups (u, g, and o).

**If you only want execute for the owner:**
```bash
chmod u+x script.sh   # u = user/owner only
```

```
Before: -rw-r--r--  (644)
After:  -rwxr--r--  (744)  ← only owner got x
```

**Why does execute matter?**

Without execute, the kernel refuses to run the file as a program. When you type `./script.sh`, the kernel checks: does the file have `x` set for the current user? No → "Permission denied." It doesn't matter that you can *read* the file — reading and executing are separate permissions.

This is a security feature. Just because a file contains valid code doesn't mean it should be runnable. Imagine a server where users can upload files — you don't want uploaded files to be executable by default.

**The subtlety: you can still run the script without `+x`:**
```bash
bash script.sh    # This works WITHOUT execute permission
./script.sh       # This REQUIRES execute permission
```

Why? `bash script.sh` runs the `bash` program (which is already executable) and tells it to read `script.sh` as input. Bash only needs *read* permission on the file. `./script.sh` asks the kernel to execute the file directly — that's where the execute bit matters.

### Reading permissions with `ls -l`:

```bash
$ ls -l script.sh
-rwxr-xr-x 1 tosin staff 2048 Jun 6 10:30 script.sh
│├──┤├──┤├──┤
│ │    │   │
│ │    │   └─ others: r-x (5)
│ │    └───── group:  r-x (5)
│ └────────── owner:  rwx (7)
└──────────── file type: - = file, d = directory, l = symlink
```

### Why this matters for DevOps:

**Scripts won't run without execute permission.** If you write a bash script and try to run `./script.sh`, it fails with "Permission denied" until you `chmod +x script.sh`. This is the #1 chmod gotcha for beginners.

**SSH keys MUST be 600.** If your private key (`~/.ssh/id_rsa`) has permissions looser than 600, SSH refuses to use it: "Permissions are too open." SSH enforces this because a private key readable by others is a security risk.

**Dockerfiles and chmod:** When you `COPY` a script into a Docker image, it might lose its execute permission. You'll see `RUN chmod +x /app/entrypoint.sh` in Dockerfiles for this reason.

**`sudo chmod -R 777 /`** — never run this. It gives everyone full access to everything on the system. People have bricked servers with this command.

## Q2: Why is `./` needed to run a script? How `$PATH` works.

### The problem:

```bash
script.sh       # "command not found"
./script.sh     # works fine
```

Both reference the same file in the same directory. Why does one work and the other doesn't?

### How the shell finds commands:

When you type a command, the shell doesn't search your current directory. It searches a specific list of directories stored in an environment variable called `$PATH`. Check yours:

```bash
echo $PATH
# Output (something like):
# /usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
```

Those are colon-separated directories. When you type `ls`, the shell searches:
1. `/usr/local/bin/ls` — exists? No → next
2. `/usr/bin/ls` — exists? No → next
3. `/bin/ls` — exists? YES → run it

That's why `ls` works without a path — it lives in `/bin/`, which is in `$PATH`. Your `script.sh` lives in `/home/tosin/projects/` or wherever you are — and that directory is NOT in `$PATH`. So the shell says "command not found."

### What `./` does:

`./` is a **relative path**. The `.` means "current directory." So `./script.sh` means "run `script.sh` from the current directory." You're giving the shell an explicit path instead of asking it to search `$PATH`.

These all work the same way — they're all explicit paths:
```bash
./script.sh                          # relative path (current dir)
/home/tosin/projects/script.sh       # absolute path
../other-dir/script.sh               # relative path (parent dir)
```

### Why doesn't the shell search the current directory?

**Security.** This is a deliberate design decision.

Imagine the current directory was searched automatically. An attacker creates a malicious file called `ls` in `/tmp/`. You `cd /tmp` and type `ls` — instead of the real `/bin/ls`, you run the attacker's `ls` which deletes your files or installs a backdoor. This is called a **PATH injection attack**.

By NOT including `.` (current directory) in `$PATH`, Unix ensures that typing `ls` always runs the system's real `ls`, never a random file that happens to be named `ls` in whatever directory you're in.

### You CAN add `.` to your PATH (but shouldn't):

```bash
export PATH=".:$PATH"    # DON'T do this — security risk
script.sh                # would now work without ./
```

This makes the current directory searchable. Convenient, but dangerous for the reason above. You'll never see this on a production server.

### The right way — add YOUR directory to PATH:

If you have scripts in `/home/tosin/bin/` that you want to run from anywhere:
```bash
export PATH="/home/tosin/bin:$PATH"
```

Now any executable in that directory works without a path prefix. Put this line in `~/.bashrc` or `~/.zshrc` to make it permanent.

### Where you'll see this in DevOps:

**Dockerfiles:** `ENV PATH="/app/bin:$PATH"` — adds the app's bin directory so you can run commands without full paths.

**CI/CD pipelines:** Tools get installed to non-standard paths. The pipeline adds them to `$PATH` so subsequent steps can find them.

**`/usr/local/bin`:** When you `brew install` something on Mac or `pip install --user` something on Linux, it goes here. This directory is in `$PATH` by default, which is why installed tools "just work."

**`which` and `type`:** When a command works but you're not sure which binary is running:
```bash
which python       # /usr/bin/python
which node         # /usr/local/bin/node
type ls            # ls is /bin/ls
```
These tell you exactly which file in `$PATH` the shell found.

## Q3: Where is `$PATH` declared?

**There's no single file. PATH is built up layer by layer as the shell starts.** Multiple files contribute to it, and the order matters.

### The chain (on Linux with bash):

```
1. /etc/environment          ← system-wide, read first, sets the base PATH
2. /etc/profile              ← system-wide, runs for all login shells
3. /etc/profile.d/*.sh       ← system-wide drop-in scripts (tools add themselves here)
4. ~/.bash_profile            ← your personal login shell config
   OR ~/.profile              ← fallback if .bash_profile doesn't exist
5. ~/.bashrc                  ← your personal non-login shell config (interactive terminals)
```

### On Mac with zsh:

```
1. /etc/zshenv               ← system-wide, runs for EVERY zsh instance
2. /etc/zprofile              ← system-wide login shell
3. ~/.zshenv                  ← personal, runs for every zsh instance
4. ~/.zshrc                   ← personal, runs for interactive shells
5. ~/.zprofile                ← personal login shell
```

Plus Mac has a special one: **`/etc/paths`** and **`/etc/paths.d/`** — Mac reads these at login to build the initial PATH. Check yours:

```bash
cat /etc/paths
# /usr/local/bin
# /usr/bin
# /bin
# /usr/sbin
# /sbin
```

### How PATH builds up:

It's additive. Each file appends to what's already there:

```bash
# /etc/environment sets the base:
PATH="/usr/local/bin:/usr/bin:/bin"

# Then /etc/profile.d/golang.sh adds Go:
export PATH="$PATH:/usr/local/go/bin"

# Then your ~/.bashrc adds your personal scripts:
export PATH="$PATH:/home/tosin/bin"

# Final result:
# /usr/local/bin:/usr/bin:/bin:/usr/local/go/bin:/home/tosin/bin
```

**Order matters.** The shell searches left to right. If `/usr/local/bin` has Python 3.11 and `/usr/bin` has Python 3.9, you get 3.11 because `/usr/local/bin` comes first. This is why you see `export PATH="/my/dir:$PATH"` (prepend) rather than `export PATH="$PATH:/my/dir"` (append) — prepending gives your version priority.

### Login shell vs non-login shell:

**Login shell** — when you first log in (SSH, console login, opening Terminal on Mac). Reads `~/.bash_profile` or `~/.zprofile`.

**Non-login shell** — opening a new tab in Terminal, or running `bash` inside an existing shell. Reads `~/.bashrc` or `~/.zshrc`.

This distinction is why people get confused: "I added PATH to `.bashrc` but it doesn't work when I SSH in" — because SSH starts a login shell which reads `.bash_profile`, not `.bashrc`. The common fix is to have `.bash_profile` source `.bashrc`:

```bash
# In ~/.bash_profile:
if [ -f ~/.bashrc ]; then
    source ~/.bashrc
fi
```

### Where tools add themselves to PATH:

When you install something, it adds itself to PATH at different levels:

- **`brew install`** → installs to `/usr/local/bin` (already in PATH)
- **`nvm` (Node Version Manager)** → adds a line to `~/.bashrc` or `~/.zshrc`
- **`pyenv`** → adds a line to `~/.bashrc` or `~/.zshrc`
- **System packages (`apt install`)** → install to `/usr/bin` (already in PATH)
- **Go installer** → drops a script in `/etc/profile.d/` 
- **Docker** → installs to `/usr/bin` (already in PATH)
- **Snap packages** → install to `/snap/bin`, snap adds this to PATH via `/etc/profile.d/`

## Q4: Does Railway use crontab to run scheduled scripts?

**No — but they borrowed crontab's syntax.**

### What crontab actually is:

`crontab` is a Linux utility that runs on a single machine. The cron daemon (`crond`) wakes up every minute, checks the crontab file, and runs whatever's scheduled. It's local to that one server — no clustering, no failover, no retry logic. If the server is down when a job was supposed to run, the job is just missed.

### What Railway (and similar platforms) actually use:

Railway, Render, Heroku, etc. have their own **distributed scheduling infrastructure**. Under the hood it's something like:

1. You define a cron schedule in their config (e.g., `0 */6 * * *` — every 6 hours)
2. Their **control plane** (a distributed system across multiple servers) tracks the schedule
3. When it's time, the control plane spins up a container, runs your script inside it, then tears the container down
4. If it fails, they can retry. If one server is down, another handles it.

They don't have a single Linux box running `crond` with your script in its crontab. The scheduling is managed by their orchestration layer — likely something built on Kubernetes CronJobs, or a custom scheduler backed by a database that tracks job state.

### What they DID take from crontab:

**The syntax.** The `* * * * *` format is universal:

```
┌───────── minute (0-59)
│ ┌─────── hour (0-23)
│ │ ┌───── day of month (1-31)
│ │ │ ┌─── month (1-12)
│ │ │ │ ┌─ day of week (0-6, Sunday=0)
│ │ │ │ │
* * * * *
```

Railway, GitHub Actions, Kubernetes, AWS EventBridge, Cloudflare Workers — they all use this same syntax. Crontab invented a notation so good that the entire industry adopted it, even though nobody uses the actual `crontab` utility in production cloud infrastructure.

### crontab vs cloud schedulers:

| | crontab | Railway / K8s CronJobs |
|--|---------|----------------------|
| Runs on | single machine | distributed infrastructure |
| If server dies | job missed | another node picks it up |
| Retry on failure | no | yes (configurable) |
| Logging | local syslog | centralized, viewable in dashboard |
| Scaling | not possible | spins up fresh container per run |
| Syntax | `* * * * *` | `* * * * *` (same) |

### Where you WILL see real crontab in DevOps:

- VMs you manage yourself (EC2 instances, your Vagrant VMs)
- Quick-and-dirty automation on a single server (log rotation, backups)
- Legacy infrastructure that hasn't moved to containers

It's still useful to know — you'll SSH into a server and need to check `crontab -l` to see what's scheduled. But for anything production-grade, platforms use their own schedulers.

## Q6: For loop uses `do`/`done`. If block uses `if`/`fi`. What's the reasoning?

**Two completely different design philosophies colliding in the same language.**

### `if`/`fi` — reverse the keyword (Algol 68 heritage)

This comes from **Algol 68**, a programming language from 1968 that influenced the Bourne shell heavily. Algol 68 used reversed keywords as block terminators:

- `if ... fi`
- `case ... esac`
- `do ... od`

The idea: the closing delimiter is the opening keyword spelled backwards. It's a visual bracket — you can scan code and immediately see what's being closed. Stephen Bourne, who wrote the original Bourne shell (`sh`) at Bell Labs in 1979, was a huge Algol 68 fan. He lifted this convention directly into his shell.

Notice `case`/`esac` is the same pattern — `esac` is `case` backwards. This is the dead giveaway that it's borrowed from Algol.

### `do`/`done` — the exception that proves the rule

If Bourne had been fully consistent with the Algol 68 convention, for loops should close with `od` (reverse of `do`). But he didn't use `od`. Why?

**Because `od` was already a Unix command.** `od` stands for "octal dump" — it displays file contents in octal format. It was a standard utility on Unix systems at the time. If the shell used `od` as a keyword, it would shadow the command — you couldn't run `od` anymore without escaping it, and existing scripts using `od` would break.

So Bourne compromised: `done` instead of `od`. It's the one place where the reversed-keyword pattern breaks, and it breaks for a purely practical reason — namespace collision with an existing tool.

### The full pattern, including the break:

| Block | Open | Close (Algol 68 style) | Actual close | Why different? |
|-------|------|----------------------|-------------|----------------|
| If | `if` | `fi` ✓ | `fi` | Follows the pattern |
| Case | `case` | `esac` ✓ | `esac` | Follows the pattern |
| Do | `do` | `od` ✗ | `done` | `od` was already a Unix command |

### Why this matters for DevOps:

It doesn't, operationally. But it tells you something about how Unix was built: **pragmatism over consistency.** The tools were written by a small group of people at Bell Labs who were solving real problems on real systems, and they made compromises when theory collided with existing infrastructure. That mentality runs through all of Unix and Linux — you'll see it again and again. Configuration formats that are "almost" consistent, commands that are "almost" standardized, flags that mean different things on different tools. It's all the same DNA.
