# DevOps Learning Log — 2026-7-28

## Q1: What is a t3.micro — is that the instance type, meaning the processor?

### Instance type ≠ processor, but it implies one

An EC2 instance type name has two parts: **family + generation** (`t3`) and **size** (`micro`).

`t3` is the **burstable general-purpose** family — designed for workloads that don't need sustained high CPU. These instances earn "CPU credits" while idle and spend them during bursts of activity. That's a different performance model from other families:

| Family | Purpose |
|--------|---------|
| `t` (t2, t3, t3a, t4g) | Burstable, general-purpose, credit-based CPU |
| `m` | General-purpose, steady/predictable performance |
| `c` | Compute-optimized (high vCPU-to-memory ratio) |
| `r` | Memory-optimized (high RAM-to-vCPU ratio) |

The `3` is the generation — AWS iterates families over time (t2 → t3 → t3a → t4g), and each generation usually brings newer underlying silicon.

`micro` is the **size** within that family — it sets vCPU/RAM. t3 sizes scale: micro → small → medium → large → xlarge → 2xlarge, etc.

### So what processor does t3 actually run on?

- **t3** → Intel Xeon Platinum (8000-series)
- **t3a** → AMD EPYC — same burstable model, different chip
- **t4g** → AWS Graviton2 (ARM), AWS's own silicon

So if you want to actually pick the processor architecture, that's the `a`/`g` suffix, not the base family name.

`t3.micro` specifically = 2 vCPUs, 1 GiB memory, Intel Xeon Platinum, credit-based burstable CPU.

### Why this matters for DevOps

Picking the wrong family is a classic cost/performance mismatch: burstable (`t`) instances are cheap and great for low/spiky traffic (dev boxes, small web servers, CI runners), but if a workload has sustained CPU load, it'll exhaust its CPU credits and get throttled hard — showing up as a mysterious performance cliff in production. That's usually the signal to move to an `m` or `c` family instance instead.

## Q2: What does an EC2 instance ARN mean?

**ARN = Amazon Resource Name.** It's AWS's universal unique identifier for *every* resource across the platform — not just EC2, but S3 buckets, IAM roles, Lambda functions, everything. Think of it as a fully-qualified path that's unambiguous no matter how many accounts, regions, or services you're working across.

### Format

```
arn:partition:service:region:account-id:resource
```

For an EC2 instance:

```
arn:aws:ec2:us-west-2:123456789012:instance/i-0abcd1234efgh5678
```

| Segment | Meaning |
|---------|---------|
| `arn` | literal prefix |
| `aws` | partition (almost always `aws`; `aws-us-gov`/`aws-cn` for GovCloud/China) |
| `ec2` | service |
| `us-west-2` | region the resource lives in |
| `123456789012` | AWS account ID that owns it |
| `instance/i-0abcd...` | resource type + the actual instance ID |

### How this relates to instance type and instance ID

Three different, easily-confused identifiers:

- **Instance type** (`t3.micro`) — what hardware profile it runs on
- **Instance ID** (`i-0abcd1234...`) — which specific instance you launched
- **ARN** — wraps the instance ID with account + region context so it's globally unique and referenceable in policy

### Why this matters for DevOps

ARNs are what you actually write into **IAM policies** — "this role can only stop/start this specific instance" is enforced by ARN, not instance type or bare instance ID. Same deal for resource tagging policies, CloudFormation/Terraform outputs, and cross-account resource sharing. If you're ever debugging an IAM `AccessDenied`, the ARN in the error message is the first thing to check against your policy's `Resource` field.

## Q3: SSH to EC2 failing with "Permission denied (publickey,...)" — full failure chain

**The headline error was misleading.** `Permission denied (publickey,gssapi-keyex,gssapi-with-mic)` looked like a credentials problem, but it was actually the *last symptom* of two upstream issues, in order.

### Failure #1 — identity file not found (wrong path)

```
Warning: Identity file ../Devops/webloginkey.pem not accessible: No such file or directory.
```

When SSH can't find the file passed to `-i`, it doesn't hard-fail immediately — it prints a warning and silently falls back to whatever other auth methods it can find: keys loaded in `ssh-agent`, default keys in `~/.ssh/` (`id_rsa`, `id_ed25519`), and GSSAPI. None of those matched what the EC2 instance's `authorized_keys` expected, so the connection failed with a "publickey,gssapi..." error that never actually involved the real key — it was never offered to the server at all.

**The trap:** `../Devops/webloginkey.pem` was a relative path from the shell's current directory (`~/aws`), and it resolved to the wrong location (wrong case/wrong directory). Relative `-i` paths are fragile for exactly this reason.

**Fix:** find the real path and use it explicitly (absolute paths sidestep the whole problem):

```bash
find ~ -iname "webloginkey.pem" 2>/dev/null
ssh -i /full/path/to/webloginkey.pem ec2-user@<public-ip>
```

### Failure #2 — key file permissions too open

Once the path was fixed, SSH found the file but refused to use it:

```
Permissions 0644 for '.../webloginkey.pem' are too open.
It is required that your private key files are NOT accessible by others.
This private key will be ignored.
```

`0644` = owner: read/write, group: read, others: read. SSH refuses any private key readable by group/others and discards it *before* even attempting auth — producing the exact same "Permission denied (publickey,...)" message as failure #1, which is what made this look like round two of the same problem rather than a new one.

**Fix:**

```bash
chmod 400 /full/path/to/webloginkey.pem
```

`400` → owner: `r--` (read only), group: `---`, others: `---` → full string `-r--------`. Fully locked down: only the owner can even read it, nobody can write or execute it. (`600`, rw for owner only, also satisfies SSH's requirement — `400` is just the tighter, more conventional choice for a key you'll never need to edit.)

After both fixes, the connection succeeded.

### Why this matters for DevOps

`.pem` files downloaded from the AWS console/CLI almost always land with loose default permissions — `chmod 400 key.pem` right after download should be a reflexive first step, not a debugging afterthought. More generally, this is a good example of **symptom vs. root cause**: the same terminal error message (`Permission denied (publickey,...)`) can mean completely different things — key not found, key ignored for bad permissions, wrong username for the AMI, wrong key pair entirely, security group blocking port 22 — and SSH's error output doesn't distinguish between them well. Reading the *lines above* the final error (the warnings) is usually where the real diagnosis lives.

### Quick reference — the SSH-to-EC2 checklist

```bash
# 1. Confirm the key file actually exists at that path
ls -la /path/to/key.pem

# 2. Lock down permissions
chmod 400 /path/to/key.pem

# 3. Connect with an absolute path, correct username for the AMI
ssh -i /path/to/key.pem ec2-user@<public-ip>   # Amazon Linux/RHEL
ssh -i /path/to/key.pem ubuntu@<public-ip>     # Ubuntu
```

## Q4: What does `cat` do — is it an editor like vim/nano?

**No — `cat` and vim/nano are opposites.** `cat` (short for "concatenate") only *reads and prints* a file's contents to the terminal, then exits immediately. There's no interactive session, no cursor, nothing to save or quit out of. vim/nano *open* a file for editing — you navigate, type, delete, and explicitly save changes back to disk before exiting.

### Basic usage

```bash
cat file.txt              # prints the whole file to the terminal
cat file1.txt file2.txt   # prints both, back to back (the "concatenate" in the name)
cat file1.txt file2.txt > combined.txt   # joins them into a new file
```

### `cat`'s siblings — for when a file is too big to just dump

| Command | What it's for |
|---------|---------------|
| `cat` | Print the entire file at once |
| `less` | Scrollable, paginated view — page through with arrows/space, search with `/`, quit with `q` |
| `head` | First N lines only (`head -20 file.log`) |
| `tail` | Last N lines only — very common for logs |
| `tail -f` | Follow a file live as new lines get appended — the classic "watch a log in real time" command |

### Why this matters for DevOps

`cat` is one of the most-used commands once you're SSH'd into servers: quickly checking a config (`cat /etc/nginx/nginx.conf`), piping a file into another tool (`cat file.json | jq .`), or building multi-line files in scripts with a heredoc (`cat <<EOF > file.txt`). But for a huge log file, `cat`-ing the whole thing floods your terminal — that's when `less` or `tail -f` become the right tool instead. Knowing when to reach for `cat` vs. `less`/`tail` is a small but constant efficiency habit in day-to-day ops work.

## Q5: Do inbound rules control what's allowed to connect to an instance — SSH on 22, HTTP on 80, by IP?

Mostly right, with one correction: it's not "AWS services" being granted permission — it's *any* traffic source (your laptop, the public internet, another server), and the inbound rule decides whether that traffic gets let in at all.

### What a Security Group actually is

A Security Group is a virtual firewall attached to an instance, with two separate rule sets:

- **Inbound rules** — traffic coming *into* the instance
- **Outbound rules** — traffic leaving the instance

Default behavior on a new security group: **all inbound blocked, all outbound allowed.** So until you add inbound rules, nothing from outside can reach the instance at all — this is exactly what produces a "connection timed out" SSH error (as opposed to the "permission denied" errors from Q3, which happen only *after* the network connection already succeeded).

### The three parts of every inbound rule

All three must match for traffic to be let through:

| Field | Example | Meaning |
|-------|---------|---------|
| Protocol | TCP | Transport protocol (TCP for SSH/HTTP/HTTPS; sometimes UDP or ICMP) |
| Port range | 22 | Which "door" on the instance the traffic is aimed at |
| Source | Your IP, or `0.0.0.0/0` | *Who* is allowed to knock on that door |

Common ports: SSH = 22, HTTP = 80, HTTPS = 443.

### Source options — this is the part that was slightly off

The "source" isn't AWS approving a service — it's an IP range or another security group:

- **Your specific IP** (`203.0.113.5/32`) — tightest; standard practice for SSH so only you can connect
- **Anywhere** (`0.0.0.0/0`) — open to the whole internet; typical for a public website on 80/443, dangerous for SSH
- **Another security group** — lets instances in your own AWS setup talk to each other without hardcoding IPs (e.g. a web-tier SG allowed to reach a database SG on port 3306)

### Stateful vs. stateless — the detail that trips people up

Security groups are **stateful**: if inbound traffic is allowed in, the response traffic automatically flows back out — no matching outbound rule needed. This is different from **Network ACLs** (a second, subnet-level firewall), which are **stateless** and require explicit rules in both directions.

### Why this matters for DevOps

For SSH to work at all: inbound rule on TCP port 22, source = your IP (or wherever you connect from). Missing that rule is exactly why a fresh EC2 instance gives "connection timed out" the very first time anyone tries to SSH in — it's a networking-layer block, one step earlier than the key-file issues from Q3. Diagnosing SSH failures in order is: (1) can I reach the instance at all? (security group/NACL/routing) → (2) does the key file exist and have correct permissions? → (3) is the username right for the AMI?

## Q6: Provisioning script for launching a web server on a t3.micro EC2 instance

### Terminology check first

"The AMI t3.micro instance" conflates two independent choices. **AMI** (Amazon Machine Image) is the OS template — Amazon Linux, Ubuntu, etc. **t3.micro** is the instance type (hardware profile, from Q1). You pick both separately at launch: "run this AMI on this instance type."

### What "provisioning script" means on EC2

It's called a **User Data script** — a bash script handed to EC2 at launch time. `cloud-init` runs it automatically as root the very first time the instance boots. No SSH-ing in required to set it up; it's baked into the launch itself.

### The script (Amazon Linux, matches `ec2-user`)

```bash
#!/bin/bash
# User data script — runs once as root on first boot

# Update packages
dnf update -y

# Install and start nginx
dnf install -y nginx
systemctl enable nginx
systemctl start nginx

# Drop in a placeholder page so there's something to see immediately
cat <<EOF > /usr/share/nginx/html/index.html
<html>
  <head><title>It works</title></head>
  <body><h1>Provisioned via user data — $(hostname)</h1></body>
</html>
EOF
```

For Ubuntu instead of Amazon Linux: swap `dnf` for `apt-get update -y` / `apt-get install -y nginx` — nginx self-starts/enables by default on Ubuntu, but the `systemctl` lines don't hurt as a safety net.

### Attaching it at launch

Paste it into the "User data" field under Advanced Details in the EC2 console launch wizard, or via CLI:

```bash
aws ec2 run-instances \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --instance-type t3.micro \
  --key-name webloginkey \
  --security-group-ids sg-xxxxxxxxxxxxxxxxx \
  --user-data file://userdata.sh
```

### Why this matters for DevOps

This ties directly back to Q5: the security group also needs an inbound rule for **TCP port 80 from `0.0.0.0/0`**, not just port 22 — otherwise nginx runs fine on the instance but is unreachable from a browser, which looks like "nothing worked" but is actually a firewall gap, not a provisioning failure. To verify a user data script actually ran, check `/var/log/cloud-init-output.log` on the instance — it captures stdout/stderr from the whole script, which is the first place to look if the page doesn't come up.

## Q7: What's the difference between PuTTY and OpenSSH?

**OpenSSH** is the SSH client/server suite built into Linux, macOS, and modern Windows (10+) — it's what's been used all session via `ssh -i key.pem ec2-user@...` from Terminal. Command-line only, open-source, the de facto standard SSH implementation across Unix-like systems.

**PuTTY** is a separate, standalone SSH client for Windows — the go-to tool before Windows shipped OpenSSH natively (that only happened around 2018). It's a GUI application: open PuTTY, enter the hostname, load a key file, click "Open" — no command line involved.

### The practical difference that actually matters: key format

| | OpenSSH | PuTTY |
|---|---------|-------|
| Key format | `.pem` (PEM-encoded) | `.ppk` (PuTTY's own proprietary format) |
| Typical use | `ssh -i key.pem user@host` | Load `.ppk` into PuTTY's session config |
| Interface | Command-line | GUI |
| Platform | Built into Linux/macOS/modern Windows | Windows-focused, separate download |

AWS hands out `.pem` files when a key pair is created — these work directly with OpenSSH. To use PuTTY instead, that `.pem` has to be converted to `.ppk` first with **PuTTYgen**, a companion tool that ships with PuTTY. Skip the conversion and PuTTY refuses to load the key outright.

### Why this matters for DevOps

Underneath, both speak the identical SSH protocol — a PuTTY connection and an OpenSSH connection to the same EC2 instance are functionally indistinguishable once established. The difference is entirely in the client tooling and key format, not the underlying security or capability. This mostly comes up in two situations: supporting a Windows teammate who's on PuTTY, or following an older AWS tutorial — a lot of legacy EC2 guides still assume PuTTY since it predates native Windows OpenSSH by over a decade. On macOS working from Terminal, OpenSSH is already the tool in use with no reason to touch PuTTY.

## Q8: What does "stateful" mean in tech, and why does it matter? (Context: security group inbound rules being stateful)

### The core idea

A **stateful** system remembers something about prior interactions and uses that memory to make decisions about future ones. A **stateless** system treats every interaction as if it's happening in total isolation, with no memory of what came before.

### Security groups, concretely

When an SSH request hits an EC2 instance on port 22, the security group's inbound rule checks it, allows it, and records that the connection exists — source IP, source port, destination IP, destination port, protocol — in a connection-tracking table (conntrack) AWS maintains behind the scenes. When the response comes back, the security group doesn't need an outbound rule to allow it — it looks up the connection table, recognizes the response belongs to an already-approved connection, and lets it through automatically.

Compare that to a **stateless** system like a Network ACL: it evaluates every packet independently, with zero memory of prior packets. A NACL needs an *explicit outbound rule* allowing return traffic — usually on the ephemeral port range (1024–65535), since that's the arbitrary high port the client OS assigned for the outgoing request. Forget that rule and the request gets in fine, but the response can't get back out — the connection just silently hangs.

### The pattern, more broadly

| | Stateful | Stateless |
|---|---------|-----------|
| Remembers prior interactions? | Yes | No |
| Examples | TCP connections, database sessions, security groups, a shopping cart | HTTP (raw), NACLs, DNS lookups, Lambda functions |
| Upside | Simpler rules, richer behavior (one rule per direction, not two) | Trivially scalable — any server can handle any request, nothing to lose |
| Downside | Harder to scale (state has to live somewhere, stay consistent) and harder to recover (lose the state, lose the context) | More verbose — every request must carry everything needed, or re-authenticate every time |

Concrete examples that make it click:

- **TCP is stateful** — it tracks a handshake, sequence numbers, and connection status (`SYN-SENT`, `ESTABLISHED`, `CLOSED`) per connection, which is how it guarantees ordered, reliable delivery. **UDP is stateless** — fire a packet and forget it, no memory of whether it arrived.
- **HTTP is stateless by design** — the server doesn't inherently know two requests came from "the same user." Cookies/sessions exist specifically to bolt statefulness onto a stateless protocol so a site can remember a login across requests.
- **Kubernetes draws the same line explicitly** — a `Deployment` is for stateless apps (any pod can die and be replaced instantly, nothing unique lost). A `StatefulSet` is for things like databases, where each pod has a persistent identity/storage that must survive restarts.

### Why it matters operationally

Two things: **scaling** and **failure recovery**. Stateless components scale trivially — spin up ten identical servers behind a load balancer, any of them can handle any request. Stateful components are much harder to scale that way, because the state has to be tracked somewhere consistent — this is why databases need replication strategies, why load balancers sometimes need "sticky sessions" to keep a user talking to the same stateful backend, and why losing a stateful component (a crashed database, an expired connection table) is far more disruptive than losing a stateless one — the whole system loses memory it was relying on, not just a server.

For security groups specifically, the practical payoff is simplicity and a fewer-footguns config: one rule instead of two, and no risk of the classic "request gets in, response never comes back" bug that stateless NACLs are prone to when the return-traffic rule gets forgotten.
