# DevOps Learning Log — 2026-8-8

## Q1: What is the point of AWS SSM (Systems Manager)?

**SSM solves the problem of: "I have 50 servers in AWS, how do I manage them without SSH-ing into each one?"**

### The core problem it replaces: SSH

Traditional server management means SSH-ing into a box, running commands, checking logs, updating packages. That works fine with 2-3 servers. At scale it breaks down:

- You need to open port 22 (SSH) on every server — that's an attack surface
- You need to manage SSH keys for every engineer across every server
- You need a bastion host (jump box) to reach servers in private subnets
- There's no audit trail of who ran what command on which server
- Running the same command on 50 servers means scripting SSH loops or using Ansible

SSM eliminates all of that. Your EC2 instances run a small agent (the SSM Agent, preinstalled on Amazon Linux and most AMIs), and that agent phones home to AWS over HTTPS. No inbound ports needed. No SSH keys to manage.

### What SSM actually does — the main features:

**Session Manager** — a browser-based or CLI shell into any EC2 instance. No SSH, no port 22, no bastion host. You open the AWS console, click "Start session," and you're in a terminal on the box. Every keystroke is logged to CloudWatch or S3. Your security team can see exactly who ran what, when.

```bash
# From your local machine — shell into an instance without SSH
aws ssm start-session --target i-0abc123def456
```

This alone is the killer feature. It means your servers can live in a fully private subnet with zero inbound ports open — no SSH, no RDP, nothing. The SSM Agent initiates outbound HTTPS connections to AWS, and Session Manager piggybacks on that.

**Run Command** — execute a command or script on one or hundreds of instances simultaneously. No SSH loop needed.

```bash
# Patch all instances tagged "Environment=production"
aws ssm send-command \
  --targets "Key=tag:Environment,Values=production" \
  --document-name "AWS-RunShellScript" \
  --parameters 'commands=["apt update && apt upgrade -y"]'
```

That one command runs `apt upgrade` on every production server in parallel and collects the output. Compare that to writing a bash loop that SSH-es into each box sequentially.

**Parameter Store** — a centralized key-value store for configuration and secrets. Instead of hardcoding database passwords in config files or environment variables on each server, you store them in Parameter Store and your app fetches them at runtime.

```bash
# Store a secret
aws ssm put-parameter --name "/prod/db/password" --value "s3cret" --type SecureString

# Your app reads it at startup
aws ssm get-parameter --name "/prod/db/password" --with-decryption
```

This is the poor man's HashiCorp Vault. For most teams it's enough. Secrets are encrypted with KMS, access is controlled by IAM policies, and there's a full audit trail of who read what.

**Patch Manager** — automates OS patching across your fleet. Define a patch baseline (which patches to apply), a maintenance window (when to apply them), and Patch Manager handles the rest. It patches servers in rolling batches so your app stays up.

**State Manager** — ensures instances stay in a desired configuration. Think of it as a lightweight config management tool. You define what should be true (this package installed, this service running, this file present) and State Manager enforces it on a schedule.

### Why it exists — the bigger picture:

SSM is AWS's answer to the question every ops team hits: **how do I manage servers at scale without building a whole infrastructure layer?** Before SSM, the answer was tools like Ansible, Chef, Puppet, or Salt — all of which require their own setup, their own servers, their own learning curve. SSM bundles the most common ops tasks into a managed service that's already integrated with IAM, CloudWatch, and the rest of the AWS ecosystem.

### The DevOps mental model:

Think of SSM as three things collapsed into one service:

| What you need | Without SSM | With SSM |
|---|---|---|
| Remote shell access | SSH + bastion host + key management | Session Manager |
| Run commands at scale | Ansible / SSH loops | Run Command |
| Secrets management | HashiCorp Vault / .env files | Parameter Store |
| OS patching | Manual or custom scripts | Patch Manager |
| Config enforcement | Chef / Puppet | State Manager |

None of these are best-in-class replacements for the dedicated tools. Ansible is more flexible than Run Command. Vault is more powerful than Parameter Store. But SSM is *good enough* for most teams and it's already there — no extra infrastructure to manage.

## Q2: Isn't SSM a security risk? If someone gains access, all infrastructure is exposed. And what commands would you run across all servers?

### How SSM access actually works — direction matters

SSM doesn't connect to your servers. Your servers connect to SSM. The SSM Agent on each EC2 instance initiates an outbound HTTPS connection to AWS's SSM service endpoints. There's no "SSM server" sitting inside your VPC with access to everything — it's a managed AWS service, and your instances register themselves with it.

### The security risk is real, but controlled by IAM

If someone compromises your AWS account with admin access, they can Session Manager into every instance. But that's true of any centralized management — compromised Ansible control node or bastion host SSH keys cause the same problem. The difference is how you limit the blast radius.

SSM uses IAM policies for fine-grained access control:

```json
{
  "Effect": "Allow",
  "Action": "ssm:StartSession",
  "Resource": "arn:aws:ec2:us-east-1:123456:instance/i-0abc123",
  "Condition": {
    "StringEquals": {
      "ssm:resourceTag/Environment": "staging"
    }
  }
}
```

That policy restricts a user to only start sessions on instances tagged "staging" — they can't touch production. With SSH, if someone has the key, they have the key. No conditional logic.

Additional safeguards: full keystroke logging to CloudWatch/S3, MFA requirements before starting sessions, and restrictions on which commands Run Command can execute.

The tradeoff: 50 servers with port 22 open and SSH keys scattered across laptops, or one IAM-controlled access path with full audit logging. SSM is the less risky option for most teams.

### Commands you'd run across all servers

**OS patching (most common):** A critical vulnerability drops (like Log4Shell in 2021), every server needs updating within hours.
```bash
apt update && apt upgrade -y
```

**Disk cleanup:** Logs fill up across your fleet, clear them before things crash.
```bash
find /var/log -name "*.gz" -mtime +30 -delete
```

**Config changes:** Rotate a TLS certificate, update an Nginx config, change a sysctl parameter across all web servers.

**Health checks:** "Is this process running on all boxes? How much disk space is left everywhere?"
```bash
df -h / | awk 'NR==2{print $5}'
```

**Security response:** Discover a compromised binary or malicious cron job — check every server immediately and kill it if found.

The pattern: something needs to happen on many machines simultaneously, and doing it one-by-one is too slow or too error-prone.

## Q3: What is a VPC (Virtual Private Cloud)?

**A VPC is your own isolated network inside AWS — not a computer, but the network that your computers (EC2 instances) sit on.**

Think of it as renting a floor in an office building. The building is AWS's data center. Other companies have their own floors (their own VPCs). You can't see their stuff, they can't see yours. But you share the same physical building, power, and elevators (the underlying hardware).

### What a VPC gives you:

An IP address range. When you create a VPC, you define a CIDR block — say `10.0.0.0/16`. That gives you 65,536 private IP addresses. Every EC2 instance, database, and load balancer inside that VPC gets an IP from that range. This is RFC 1918 private addressing — `10.x.x.x` is one of those reserved ranges.

### Inside the VPC, you carve out subnets:

- **Public subnet** (`10.0.1.0/24`) — has a route to the internet via an Internet Gateway. Web servers go here.
- **Private subnet** (`10.0.2.0/24`) — no direct internet access. Databases go here. They can reach the internet outbound through a NAT Gateway (for updates, API calls), but nothing from the internet can reach them inbound.

This maps directly to the Vagrant dual-NIC setup — `eth0` for internet (NAT) and `eth1` for internal communication (host-only). AWS formalized that pattern into subnets and route tables.

### The "private" means network isolation

Your `10.0.0.0/16` is completely separate from another AWS customer's `10.0.0.0/16`. They can use the exact same IP range — doesn't matter. Traffic never crosses. AWS's networking layer enforces the boundary.

### The mental model:

- **VPC** = your private network
- **EC2 instances** = computers on that network
- **Subnets** = rooms within the network (public-facing vs internal)
- **Security groups** = firewall rules on each computer's door
- **NAT Gateway** = how private-subnet instances reach the internet outbound without being reachable inbound

## Q4: What is EBS (Elastic Block Store) and why should a DevOps engineer care?

**EBS is the virtual hard drive for EC2 instances.** It's persistent storage that exists independently of the VM.

### The PC analogy:

Your Mac has a built-in SSD soldered to the motherboard. If the motherboard dies, you lose the SSD too. That's like EC2 **instance store** (ephemeral storage) — fast, but dies with the machine.

EBS is like an external SSD plugged in via USB. If your Mac dies, unplug the drive, plug it into a new Mac, data is still there. EBS volumes are network-attached storage that exist on AWS's storage infrastructure, separate from the physical server running your EC2 instance. You can detach from one instance and attach to another.

### Why DevOps engineers care:

**1. Your database lives on EBS.** If running Postgres or MySQL on EC2, the data files sit on an EBS volume. Wrong type = slow queries. Wrong size = disk fills at 3am. No snapshots = no disaster recovery.

**2. EBS types = choosing between HDD and NVMe SSD:**

| EBS Type | PC Analogy | Use Case | Cost |
|---|---|---|---|
| `gp3` (General Purpose SSD) | Standard SATA SSD | Most workloads, boot volumes | Cheap |
| `io2` (Provisioned IOPS SSD) | High-end NVMe | Databases needing guaranteed speed | Expensive |
| `st1` (Throughput HDD) | Big spinning hard drive | Log processing, sequential reads | Very cheap |
| `sc1` (Cold HDD) | Archive drive in a closet | Backups you rarely access | Cheapest |

Picking `io2` for a log archive is burning money. Picking `sc1` for a production database guarantees slow queries.

**3. Snapshots = backups.** Snapshot an EBS volume at any point — creates a point-in-time copy stored in S3. Database corrupts, restore from snapshot. Equivalent of Time Machine on Mac, but for a server's disk.

**4. Resize without downtime.** Disk filling up at 50GB? Expand to 200GB without stopping the instance. This doesn't exist in the physical world.

### The gotcha:

EBS volumes are tied to a single Availability Zone. Instance in `us-east-1a`, volume in `us-east-1b` — can't attach. To move data across AZs, snapshot the volume and restore it in the other AZ.

## Q5: Why is EBS named `/dev/xvda` in AWS but `/dev/nvme0n1` inside the OS?

**Because AWS has two generations of virtualization, and each exposes disks differently.**

### Generation 1: Xen (old)

AWS originally ran on the **Xen hypervisor**. Xen presented disks to VMs as "Xen Virtual Disks" — hence `/dev/xvda`, `/dev/xvdb`, etc. Older instance types like `t2.micro`, `m4.large`, and `c4.xlarge` use Xen. If you SSH into a `t2.micro` and run `fdisk -l`, the disk actually shows up as `/dev/xvda`.

### Generation 2: Nitro (new)

AWS built their own hypervisor called **Nitro** starting around 2017. Nitro exposes disks as NVMe devices — industry-standard, faster, lower overhead. Instance types like `t3.micro`, `m5.large`, `c5.xlarge` and everything newer use Nitro. That's why your `t3.micro` shows `/dev/nvme0n1`.

### Why the AWS console still says `/dev/xvda`:

Backward compatibility. The console uses Xen-style names as a *logical identifier* regardless of which hypervisor your instance runs on. It's the "label" AWS gives the volume. The OS sees the *actual* device driver name, which on Nitro is NVMe.

### The mapping:

| AWS Console | Xen instance (t2, m4) | Nitro instance (t3, m5) |
|---|---|---|
| `/dev/xvda` | `/dev/xvda` (matches) | `/dev/nvme0n1` (different) |
| `/dev/xvdb` | `/dev/xvdb` (matches) | `/dev/nvme1n1` (different) |

### Why Nitro matters for DevOps:

If you write a script that references `/dev/xvda` (because that's what the console shows), it will fail on a Nitro instance. You need to use `/dev/nvme0n1` instead, or use `lsblk` to discover the actual device name dynamically. This is a real gotcha when migrating from older to newer instance types.

The AWS console shows the device as `/dev/xvda` (Xen naming), but inside the instance it appears as `/dev/nvme0n1` (NVMe naming).

`Disk model: Amazon Elastic Block Store` — the disk literally identifies itself as EBS.

### The three partitions:

- **`/dev/nvme0n1p1` (8G, Linux filesystem)** — where the OS and files live. The main partition.
- **`/dev/nvme0n1p128` (10M, EFI System)** — boot partition containing the bootloader (GRUB). Every modern computer has this.
- **`/dev/nvme0n1p127` (1M, BIOS boot)** — compatibility shim for legacy BIOS booting on older instance types.

"Partition table entries are not in disk order" — the partitions aren't numbered in the order they appear physically on disk. `p127` and `p128` sit before `p1` on the disk (lower sector numbers). Harmless — just how Amazon built the AMI.

**Sector math:** 8 GiB = 16,777,216 sectors × 512 bytes = 8,589,934,592 bytes.

## Q6: What is a hypervisor — is it like a kernel?

**A hypervisor sits below kernels. It's what lets multiple kernels share the same hardware.**

A kernel is one-to-one: one kernel manages one machine's hardware. A hypervisor breaks that by creating fake hardware (virtual CPUs, virtual disks, virtual NICs) and giving each VM its own set. Each VM's kernel thinks it's talking to real hardware, but it's talking to the hypervisor, which multiplexes everything to the real hardware.

```
hardware → hypervisor → fake hardware → kernel → shell → you
```

VMware Fusion on your Mac is a hypervisor. AWS Xen and Nitro are hypervisors. They all do the same thing — trick kernels into thinking they own the hardware.

## Q7: Disk partitioning — reading `fdisk -l` output

**A partition is a section of a disk that the OS treats as an independent storage area.** One physical (or virtual) disk gets divided into partitions, each with its own purpose. Same concept as your Mac's disk being split into a system partition and a recovery partition.

### The three partitions on a default EC2 Amazon Linux instance:

```
Device           Start      End  Sectors Size Type
/dev/nvme0n1p1   24576 16777182 16752607   8G Linux filesystem
/dev/nvme0n1p127 22528    24575     2048   1M BIOS boot
/dev/nvme0n1p128  2048    22527    20480  10M EFI System
```

**`p1` (8G, Linux filesystem)** — the main partition. This is where `/`, `/home`, `/var`, `/tmp` and everything else lives. Your OS, your apps, your data — all here.

**`p128` (10M, EFI System Partition)** — contains the bootloader (GRUB). When the machine powers on, the firmware reads this partition first to figure out how to start the OS. Every modern computer has one — your Mac has one too. You never touch it.

**`p127` (1M, BIOS boot)** — a tiny compatibility partition for older boot methods. Some instance types use legacy BIOS instead of UEFI. This partition holds the bootloader code for that scenario. Also never touched.

### Key concepts:

**Sectors** — the smallest addressable unit on a disk. Each sector is 512 bytes. The Start/End columns tell you where each partition physically sits on the disk. `p128` starts at sector 2048 and `p1` starts at sector 24576 — so the boot partitions sit at the very front of the disk, and the main filesystem takes up the rest.

**GPT (GUID Partition Table)** — the partitioning scheme (`Disklabel type: gpt` in the output). GPT is the modern standard, replacing the older MBR (Master Boot Record) scheme. MBR could only address disks up to 2 TiB and supported max 4 primary partitions. GPT supports disks up to 9.4 ZB (zettabytes) and up to 128 partitions. Every modern system uses GPT.

**"Partition table entries are not in disk order"** — the partition numbers (`p1`, `p127`, `p128`) don't match their physical order on disk. Physically it's `p128` → `p127` → `p1` (by start sector). The numbering is just a label. This is normal for AWS AMIs.

### Useful commands for working with partitions:

```bash
lsblk              # tree view of disks and partitions — cleanest output
fdisk -l            # detailed partition table (what you ran)
df -h               # shows mounted partitions and how full they are
mount               # shows what's mounted where
blkid               # shows partition UUIDs and filesystem types
```

### When you'd partition a disk in DevOps:

- **Attaching a new EBS volume** — it arrives as a raw disk with no partitions. You partition it, format it (`mkfs.ext4`), and mount it.
- **Separating `/var/log`** — put logs on their own partition so a log explosion doesn't fill the root filesystem and crash the OS.
- **Database storage** — give Postgres its own dedicated partition/volume with the right EBS type and IOPS.
