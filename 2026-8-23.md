# DevOps Learning Log — 2026-8-23

## Q1: Why would you want to copy a snapshot from one AWS account to another?

### The core idea

An EBS snapshot (or an AMI, which is basically a snapshot + boot metadata) lives in the AWS account and region where it was created, and by default only that account can use it. Copying a snapshot to another account isn't really about the disk data — it's about crossing a security/billing/ownership boundary on purpose.

### The real reasons you'd do this

| Reason | What's actually happening |
|---|---|
| **Multi-account strategy** | Most mature AWS setups don't put everything in one account — they split prod, staging, dev, security, and sandbox into separate accounts (AWS Organizations / Control Tower "landing zone" pattern). A snapshot taken in prod needs to be copied into staging to seed a realistic test environment. |
| **Disaster recovery / blast radius** | If your prod account is ever compromised (leaked credentials, a bad IAM policy, whatever), and your backups live in that same account, an attacker can delete your backups too. Copying snapshots into a separate, locked-down "backup" account means a full account compromise doesn't take your recovery point with it. |
| **Golden AMI distribution** | A platform/security team builds a hardened, patched "golden image" (approved AMI) in one central account, then shares/copies it out to every application team's account so nobody builds their own insecure base image. |
| **Mergers, acquisitions, org restructuring** | Company reorganizes AWS accounts (very common), and existing infrastructure/data has to move to new account IDs without recreating it from scratch. |
| **Selling or sharing with a third party** | You want to give a customer, vendor, or partner a machine image or dataset without giving them access to your actual account (no IAM users, no console access — just the artifact). AWS Marketplace AMIs work exactly this way. |
| **Cross-region + cross-account DR combo** | Real disaster recovery plans often do both at once: copy the snapshot to another region (survives a regional outage) AND another account (survives an account-level compromise or accidental deletion). |
| **Cost/billing isolation** | Some orgs want storage costs for archived snapshots billed to a dedicated "archive" account rather than sitting on the engineering team's bill. |

### How the mechanics actually work

1. **Share the snapshot** from the source account — this doesn't copy any bytes yet, it just grants permission:
```bash
aws ec2 modify-snapshot-attribute \
  --snapshot-id snap-0123456789abcdef0 \
  --attribute createVolumePermission \
  --operation-type add \
  --user-ids 111122223333   # the destination account ID
```
2. **Copy it** from the *destination* account (you pull it in, the source doesn't push):
```bash
aws ec2 copy-snapshot \
  --source-region us-east-1 \
  --source-snapshot-id snap-0123456789abcdef0 \
  --description "Copied from prod account"
```

### The #1 gotcha: encryption

If the snapshot is encrypted (and by default in most accounts now, it is), sharing the snapshot alone isn't enough. The destination account also needs permission to use the KMS key that encrypted it — otherwise the copy fails with an access-denied error that has nothing obviously to do with KMS at first glance. You either:
- add the destination account to the KMS key policy, or
- copy with `--kms-key-id` pointing at a key the destination account owns/can access.

This trips up almost everyone the first time they do a cross-account snapshot copy.

### Why this matters for DevOps

This is the pattern behind real backup strategies (not "click snapshot in the console and hope"), behind how platform teams distribute standardized AMIs at scale, and behind how DR runbooks actually get tested — because a DR plan that only survives losing a server but not losing the account isn't really a DR plan.

## Q2: What are the different types of load balancer on AWS?

### The plain-English version first

A load balancer is a receptionist standing in front of a group of servers, deciding who gets sent where. AWS (Elastic Load Balancing, or "ELB") offers four flavors of receptionist, each built for a different situation.

| Type | Layer it operates at | Plain-English role | Best for |
|---|---|---|---|
| **Application Load Balancer (ALB)** | Layer 7 (application) | Reads the actual request (URL path, hostname, headers) and routes intelligently | Web apps, REST APIs, microservices |
| **Network Load Balancer (NLB)** | Layer 4 (transport) | Forwards raw TCP/UDP connections as fast as possible, no content inspection | Extreme performance, low latency, non-HTTP protocols, needs a static IP |
| **Gateway Load Balancer (GWLB)** | Layer 3 (network) | Transparently routes all traffic through third-party security appliances | Firewalls, IDS/IPS, deep packet inspection |
| **Classic Load Balancer (CLB)** | Layer 4/7 (blended, legacy) | The original ELB from before AWS split load balancing into specialized types | Legacy apps only — AWS actively discourages new use |

### Application Load Balancer (ALB) — the smart one

ALB understands HTTP/HTTPS. It can look inside a request and route based on:
- **Path**: `/api/*` → one target group, `/images/*` → another
- **Host header**: `blog.example.com` vs `shop.example.com` on the same load balancer
- **Query strings, headers, even the HTTP method**

This is what makes ALB the backbone of microservices architectures — one load balancer, many services behind it, routed by content. It also natively supports WebSockets, HTTP/2, and can route directly to Lambda functions, not just EC2 instances or containers.

### Network Load Balancer (NLB) — the fast one

NLB doesn't inspect anything above the transport layer — it just moves TCP/UDP packets. Because it's not doing any "reading," it can handle millions of requests per second with ultra-low latency. Two things make it distinct:
- **Static IP per Availability Zone** (ALB's IP can change; NLB's doesn't) — important if a client needs to whitelist a fixed IP.
- **Preserves the source IP** of the client all the way to the target by default, which ALB doesn't do the same way (ALB relies on `X-Forwarded-For` headers instead).

### Gateway Load Balancer (GWLB) — the security checkpoint

GWLB is fundamentally different from the other two — it's not balancing load across *your application servers*, it's balancing load across a fleet of *third-party network appliances* (firewalls, intrusion detection systems from vendors like Palo Alto, Fortinet, Check Point). Traffic flows through it transparently using a protocol called GENEVE, gets inspected, and continues on its way. Most engineers won't touch this unless they're building out network security infrastructure.

### Classic Load Balancer (CLB) — the legacy one

CLB predates the Layer 4/Layer 7 split. It does a bit of both, poorly compared to the specialized versions, and lacks features like path-based routing. AWS keeps it running for backward compatibility but explicitly recommends migrating off it — you'll mostly encounter it in older AWS accounts that haven't been modernized.

### The subtlety: how they pick a target

| Type | Routing decision based on |
|---|---|
| ALB | Content of the HTTP request |
| NLB | Connection (IP + port), not content |
| GWLB | Flow, then hands off to an appliance which decides |
| CLB | Round robin / least connections, no content awareness |

### Why this matters for DevOps

Picking the wrong one is a common early mistake: using NLB when you actually need path-based routing (you'll have to build that logic yourself downstream), or using ALB when you need a static IP a partner's firewall can whitelist (you'll be stuck fighting DNS instead). In real infrastructure, it's common to see them combined — e.g., an NLB in front of an ALB to get a static IP plus content-based routing, or a GWLB inspecting traffic before it ever reaches the ALB.

## Q3: What do "Layer 3", "Layer 4", and "Layer 7" mean? (OSI model refresher)

### The postal analogy

Sending data across a network is like mailing a letter — it gets wrapped in layers, like nested envelopes, and each layer has exactly one job. That's the **OSI model**: 7 layers, each responsible for one piece of getting data from your device to a server and back.

### The 7 layers, top to bottom

| Layer | Name | What it does | Real-world example |
|---|---|---|---|
| 7 | Application | The actual content/meaning of the request | HTTP request — "GET /login" |
| 6 | Presentation | Formatting/encryption of the data | TLS/SSL, compression |
| 5 | Session | Keeping a conversation open between two devices | A login session staying active |
| 4 | Transport | Reliable delivery as a stream/connection | TCP, UDP, ports (`:443`, `:80`) |
| 3 | Network | Getting data from one network to another, by address | IP addresses, routers |
| 2 | Data Link | Getting data across one physical/local link | MAC addresses, switches |
| 1 | Physical | The actual electrical/optical signal | Cables, Wi-Fi radio waves |

Layers 1, 2, 5, and 6 rarely come up day-to-day in cloud/DevOps work. The three that matter constantly — especially for load balancers — are **3, 4, and 7**.

### Layer 3 — Network layer ("where is it going?")

Layer 3 is purely about **addresses and routing** — IP addresses. A device at this layer only knows "this packet needs to reach `10.0.1.5`"; it has zero awareness of what's inside — not a website, not a database query, nothing. It's a postal worker who reads the street address on an envelope and routes it toward the right city, without ever opening it.

**Where GWLB fits**: it operates here because it's not inspecting *what* the traffic is — it's making sure traffic gets routed through the correct path (a security appliance) based purely on network-level routing.

### Layer 4 — Transport layer ("which conversation is this part of?")

Layer 4 introduces **TCP and UDP**, and this is where **ports** live (`:80` for HTTP, `:443` for HTTPS, `:22` for SSH). A device at this layer knows "this is part of a connection between IP `A` port `50213` and IP `B` port `443`" — but still never opens up the actual data inside. It's a mail sorter reading "Attn: Sales Dept" on the envelope and routing it to the right department without reading the letter.

**Where NLB and CLB fit**: NLB forwards TCP/UDP connections based on IP + port at extremely high speed, without inspecting content. CLB operates in a blended, older way across both Layer 4 and Layer 7.

### Layer 7 — Application layer ("what does it actually say?")

Layer 7 is the top of the stack — the real content of the request. This is HTTP/HTTPS: URLs, headers, cookies, request bodies — everything you as a human actually interact with. This is the postal worker actually opening the envelope and reading the letter: "this person specifically wants the login page."

**Where ALB fits**: because it operates here, it can do path-based routing (`/api` vs `/images`), route by hostname, inspect headers — real content-aware decisions.

### The subtlety: the tradeoff is speed vs. intelligence

The lower the layer a piece of infrastructure operates at, the less it understands about the traffic, but the faster and more efficient it can be — fewer things to inspect means less work. The higher the layer, the smarter and more flexible the routing, but with more overhead. This tradeoff is the entire reason AWS didn't build one universal load balancer — ALB (Layer 7), NLB (Layer 4), and GWLB (Layer 3) each trade intelligence for speed differently, and picking the right one means picking the right tradeoff for your traffic.

### Why this matters for DevOps

Nearly every troubleshooting conversation in networking eventually comes down to "which layer is this actually failing at?" A DNS issue is layer-adjacent but not OSI layer 3/4/7 in the strict sense; a "connection refused" error is typically Layer 4 (nothing's listening on that port); a "502 Bad Gateway" is typically Layer 7 (something's listening, but the application response is broken). Being able to place a symptom at the right layer is what separates "randomly restarting things" from actually diagnosing the problem.
